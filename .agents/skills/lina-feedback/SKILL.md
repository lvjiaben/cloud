# 反馈修复

处理已有实现的缺陷、遗漏或改进建议。规则入口为`AGENTS.md`、`.agents/rules/openspec.md`和`.agents/rules/context-loading.md`；按实际影响读取领域规则，不在技能中重复维护规则。

## 分诊与定位

1. 根据问题、路径和相关能力定位源码与规范，先向用户报告根因或有证据的假设，再修改。
2. 自主选择处理路径并简短告知依据：
   - `direct-fix`：局部实现修正、文案或轻量治理修改，不改变长期业务或框架契约。不创建形式化文档。
   - `openspec-existing`：直接修正某个活跃变更的目标、验收或实现缺口，仅更新相关任务和规范。
   - `openspec-new`：新增耐久能力、业务/API/数据/权限契约、跨模块设计或长期治理门禁，创建最小必要变更记录。
   - `no-change`：仅讨论、已有覆盖或必须先澄清，说明证据与待解决条件。
3. 活跃变更只做候选，不因存在变更就自动追加。先看目录与名称，必要时用`openspec list --json`；多个候选确有归属歧义才询问。
4. 业务或交互结论不明确时，按顶层澄清门禁暂停依赖的实现；确认后同步偏好与受影响活跃规范。

## 实施与闭环

- 先读相关任务与完整的目标`Requirement`及其`Scenario`；`proposal.md`、`design.md`及其他规范仅在范围、设计或依赖相关时读取，不展开全部变更。
- 同一根因合并处理。已有规范正确则修实现；规范缺失或改变则先更新相关规范。新建变更时遵循当前 schema 的必要产物，不硬造大篇幅模板。
- 读取与证据复用遵循`context-loading.md`：同一任务未变化且正文仍可见的内容可复用；跨会话、正文丢失、文件变化或范围扩展时重新读取必要内容。
- 影响分析、验证与任务记录按`openspec.md`和命中领域规则执行。行为修复验证相关行为；治理修改采用静态检查、文件检查或规范校验。仅在新增或变化路径、失败或覆盖缺口需要时补跑验证，不重复无变化路径的已通过检查。
- 调用`lina-review`审查本任务范围，满足实现、验证和审查门禁后才标记完成；独立新问题重新分诊，不自动扩大任务。
- 结果简述处理路径、根因、修改范围、实际验证、审查结论和剩余阻断。不得自动提交、推送或归档。
