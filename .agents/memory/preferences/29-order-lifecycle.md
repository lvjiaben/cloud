## 订单取消、到期与风险审核规则

- 商家后台配置的付款有效分钟数只影响后续新结账；结账时必须把同一个数据库截止时间固化到订单、待付账单和本地库存预留，后续改策略不得追溯改旧订单。客户结账幂等继续复用唯一的报价结账摘要，禁止为重复点击另建第二套幂等事实。
- `pending_payment`和`manual_review`订单只有在账单零支付、零可退/已退款、没有支付分配、活动资金锁定或账本流水、库存仍全部持有，且没有任何履约意图越过插件调用边界时才能本地取消。订单、账单、库存、通用交付事实、待处理审核、营销名额、取消记录和 Outbox 必须在同一 PostgreSQL 事务提交，任何异常都失败关闭。
- 到期扫描只在宿主主节点托管任务中运行，使用数据库时间、固定批量上限与`FOR UPDATE SKIP LOCKED`逐条领取；扫描事务内不得调用支付渠道、Provider、通知或其他外部系统。
- `payment_processing`订单取消只能先创建唯一`pending_payment_closure`意图，不能提前取消账单或释放资源。支付 owner 必须先锁同一订单行再创建支付尝试，并用明确的关单结果、引用和证据摘要回报；确认成功或结果未知必须转人工，迟到成功款处理仍由支付阶段负责，禁止复活旧订单。
- 取消订单后的迟到成功款只能由后台人员分配给同一客户已经自行创建的另一张未付新订单，系统不得自动建单，也不得复活旧订单。新订单仍须重新通过当前价格、库存、实名和风险检查，且待归属款的币种、金额必须与新订单当前未付金额完全一致；不一致时只能原路退款。若支付通道不能自动原路退款，系统创建人工原路退款任务，资金继续保持待处理，直到后台上传退款凭证并确认完成，禁止自动转入客户余额。
- 风控批准与驳回是两条独立后台资源和两个精确权限，只允许默认商家的直接活动员工调用，禁止冒充和不可表达的数据范围。批准只解除风险门禁，不能绕过库存人工确认或人工履约；驳回必须复用统一取消事务。审核只保存证据摘要，决定与业务审计同事务，幂等重放必须同时匹配决定、请求、证据和操作人。
