# 代理质量与完整交付

## 用户确认：2026-10-22

用户反馈节省`Token`后对话质量下降、小问题频发，明确要求以聪明、正确解决问题为前提，完成全部优化后再汇报，并接管项目下四个既有对话继续修复。

- 优先级为正确理解和解决问题、完整交付、效率与成本。节省无关读取、重复输出和无效查询，不节省必要分析、权威上下文、跨模块排查或真实验证。
- “全部修好”“继续完成”等授权覆盖已确认目标及其必要依赖，不能只做一个容易的局部项后要求用户再次说继续。后续反馈默认补充原目标，只有用户明确替换或取消时才改变目标。
- 当前代码、任务勾选和过去测试通过都不是产品正确的充分证明。用户反馈复发、运行配置改变或其他对话修改依赖时，重新核查受影响链路，区分源码、构建产物、正在运行的版本和实际业务结果。
- 已确认的业务边界保持有效。自主处理内部实现与基础交互，真实业务歧义和外部授权仍按原规则处理；不能以质量优先为由修改禁止修改的宿主或扩大第三方写入权限。
- 本次四对话接管授权仅用于本轮项目协作；不形成今后任意跨对话发送、启动、重启共享环境或第三方写入的永久授权。

执行方式由[上下文规则](../../rules/context-loading.md)与[工作流规则](../../rules/openspec.md)维护，不在本主题复制流程。

## 追加复查：2026-10-22

用户在首轮汇报后要求“多检查几次多优化两次”。本次继续四个对话，各做两轮不同角度的检查和必要修正；优先发现旧验证盲区，不能把重复测试数量当质量，也不为满足轮数制造修改。该次要求不转成今后所有任务都必须两轮审计。
