## 正式设计架构决策

### 2026-10-22：资源操作归入业务对象

用户确认`SSL`证书、魔方云服务器、服务器管理、自动化任务和对接日志不再独立贡献后台顶层入口，有明确归属的操作收进对应订单或客户产品管理页面；服务端按当前对象校验权限和归属，不以浏览器筛选替代数据范围。供应商容量、健康检查等无订单/产品归属的全局运维放到供应商接口配置页；尚不能精确关联产品的接口日志只在该接口上下文展示。

### 2026-10-28：服务器与资源快捷入口

用户确认保留现有业务归属，仅在“服务器与资源”下补明显快捷入口。服务器管理导航到客户产品管理，供应商运维导航到现有供应商接口配置的运维页签，并保留附属资源续费待办；不恢复退役的跨客户服务器目录、独立任务或日志业务页面。

### 2026-10-16：自动化接口填写根地址并隐藏证书指纹

用户明确要求删除日常接口表单的“证书指纹（可选）”，魔方云只填写含自定义后台路径的根地址，例如`https://host/W5SHNaHntv/`，不手工填写`/v1`或登录路由。连接器通过拥有方校验的声明补齐自己的版本前缀，已有匹配版本不得重复追加。删除输入不清空原有已保存的证书信任，也不关闭默认的`HTTPS`证书验证。本条替代旧的要求普通运营人员手填证书指纹或补接口路由的交互。

### 2026-10-16：自动化接口日常维护不绑定插件发布号

用户明确要求接口与插件版本解耦，不因找不到保存时的插件配置版本而禁止编辑或测试。自动化接口的配置表单、配置校验和显式连接测试使用当前已安装启用且同一提供方、契约兼容的连接器；发布号或摘要变化不要求管理员先恢复旧版或点击更新。缺少连接器、提供方不匹配或契约不兼容时给出对应诊断。历史订单、任务和配置修订的执行证据保留，不由日常编辑或连接测试改写。本条替代旧的日常维护必须匹配保存时发布证据的限制。

### 2026-10-15：操作登录限制调整

用户最新明确要求取消各接口额外的近期重新登录等复杂操作限制。具有对应权限且当前登录会话有效的用户可以直接操作，不再要求五分钟内重新完整登录。本条替代下文及其他主题、规范中额外的近期登录要求。保留正常身份认证、角色权限、客户和租户归属、秘密加密、审计、精确操作绑定、防重复扣费、版本冲突、真实供应商能力及已使用资源的历史保护；不得以恢复连通性为由伪造成功或绕过收费规则。

- 首版总体`OpenSpec`变更为`openspec/changes/add-idc-server-operations-platform/`，提案、总体设计、分域规范和实施任务以该目录为当前正式设计事实来源。
- `openspec/changes/add-idc-server-operations-platform/coverage.md`是“魔方财务、V10、市场与用户需求 → 新 capability → 实施任务 → E2E → 批准例外”的首版覆盖门禁；任何标记首版强制或能力门禁的行缺少实现和验收证据都不得发布。
- 插件体系固定分为两个面向对象不同、底层隔离原则一致的层次。第一层是`LinaPro`开发框架面向开发者：开发者通过源码插件组合系统能力，业务实现闭环在插件内，不污染框架宿主。第二层是当前基于`LinaPro`开发的服务器业务与财务平台面向商家用户：商品、订单、账务、通知、资源、官网等基础业务拥有方作为强制内置源码插件构成平台地基，正常贡献业务菜单和页面，但不出现在商家可管理的插件列表中；商家只需要安装、配置和管理受治理的动态`WASM`扩展插件。
- 平台用户安装的`WASM`插件只能扩展内置业务拥有方明确发布的扩展点，并复用宿主提供的身份、权限、数据范围、主题、语言、菜单槽位、异步任务和安全调用桥。它不能修改宿主或内置业务拥有方源码，不能绕过领域规则，不能直接访问其他插件私有状态或数据。平台制定的是可声明、可校验、可授权的扩展规范，目标是让用户通过安装不同`WASM`插件获得不同业务能力，而不改动或破坏业务财务平台本身。
- “内置插件隐藏”只表示不在统一插件管理列表中展示安装、停用、卸载等入口，不表示隐藏它所拥有的商品、订单、财务、通知、资源、官网内容等正常业务菜单和页面。内置业务拥有方通过自己的业务菜单使用；统一插件管理只展示商家真正能够上传、安装、升级、停止新业务、停用和卸载的托管`WASM`插件。
- 正式交付复用同一插件宿主，由内置源码业务拥有方和托管动态扩展插件共同组成。官方基础拥有方直接使用`idc-core`、`idc-payment`、`idc-resource`、`idc-compliance`、`idc-notify`、`idc-channel`、`idc-ai`、`idc-portal`、`shared-services`、`org-core`和`content-notice`等无品牌前缀 ID；`tenant-core`、组织管理和内容管理-通知公告都属于强制内置能力，必须随系统安装启用、禁止停用卸载，并从商家插件管理列表隐藏，但继续正常贡献部门、岗位和通知公告业务菜单。智简魔方云、`SSL`、短信供应商、支付网关和`idc-zjmfmigrate`等可替换、可按需安装的能力使用托管动态插件，不能因为首版提供就写成内置源码插件。
- `idc-core`是客户、商品、营销、购物车、订单、应收账单、资金账本、退款申请与业务结果、信用账户、服务权益、业务操作、工单、销售、佣金、本地合规门禁投影、事务`Outbox`、幂等和业务审计的唯一权威拥有者。`payment`独占渠道支付/退款尝试与证据，`resource`独占 Provider、上游资源映射与任务，`compliance`独占认证案件、合同文件和`tax_invoice`，`notify`独占投递证据，`channel`独占令牌、订阅和下游请求证据；外围插件不得直接改核心表。
- 开放`API`订单、付款和服务统一归凭据绑定客户，对方终端客户由对方系统管理；原企业自有与委托双模式决定已由[客户业务与开放 API 规则](76-customer-business-openapi.md)替代。
- 下游渠道的服务器变配和换`IP`固定使用“两阶段报价再执行”：第一次请求只按本地正式价格、当前服务、资源策略和可用容量生成短期冻结报价，不扣余额或信用、不调用上游；渠道明确提交报价编号并选择余额或授信结算后，系统重新核对服务版本、报价有效期、付款义务人、服务所有者、额度和资源预留，在同一核心交易链路完成结算后才创建`business_operation`并调用资源拥有方。升配及收费换`IP`结算成功后立即执行，降配在当前周期到期时执行；免费操作仍保留零金额报价和审计，但不得创建假账单、假支付或假结算。重复确认必须复用同一报价、订单、账单和业务操作，失败或结果未知时不得重复扣款或盲目重放上游动作。
- 开放`API`由管理员选择客户并授予接口，生成`AppID/AppSecret`；不再以企业渠道审批作为前置条件，凭据和客户边界以[开放 API 规则](76-customer-business-openapi.md)为准。
- 跨插件禁止导入其他插件的`backend/internal`、跨插件直接查表、建立跨插件数据库外键或依赖同步站内`HTTP`完成业务事务。订单、账单、资金、库存预留和`Outbox`在`core`本地事务中提交，外部副作用最终一致。
- `2026-10-25`用户确认业务性能优先：所属业务的本地权威数据直接通过拥有方数据库集合读取，不为普通查询重复检查插件安装或扫描全部插件声明；只有实际使用可替换扩展、变更绑定及必要执行准入时保留插件状态与授权检查。同一生命周期锁内已确认的证据可在本次回调内复用，退出后失效；不能把优化扩大为跨拥有方私表访问或绕过实际执行校验。
- 上述跨插件边界必须由仓库测试持续执行：`Go AST`只允许依赖其他`IDC`插件的`backend/cap/*`公开契约，并扫描生产`Go`字符串和插件`SQL`中的外插件表前缀及`REFERENCES`；迁移插件也不得以迁移为由绕过公开导入能力直接写目标插件表。
- 客户域不采用一刀切的软删除：客户普通资料经批准注销后按策略匿名化；等级、分组、标签、自定义字段等配置使用停用或归档；同意、备注版本、跟进、黑名单、风险和其他证据历史保留可追溯状态，不能用普通删除抹去。
- 客户运营记录首版按推荐方案固定：后台备注只能追加，写错时新增更正备注并把旧备注标成已撤回，旧正文和关联关系继续保留；跟进先建立计划，之后只能明确完成或取消，不覆盖历史；黑名单先提交为不生效的待审批记录，再通过独立按钮批准或驳回，只有批准后才生效，生效后可以明确撤销。首版不强制第二个人审批，同一名有权后台员工可以提交后再执行批准，但两次动作和每次审计都必须分开；这些操作统一要求`idc:admin:customer:update`权限、客户数据范围和数据库事务审计。
- 后台客户协助固定为 15 分钟、单次使用的完整客户模拟登录：要求直接活动员工、独立精确权限、目标客户数据范围；2026-10-12用户确认点击直接模拟登录，不再要求确认弹窗、填写原因或工单，系统自动记录启动说明；同一员工同一时刻只保留一个活动会话，新会话结束旧会话。协助会话以目标客户真实身份进入同一套`web-customer`控制台，菜单、查询和写操作能力与该客户本人一致，不再额外禁止付款、退款、密码与密钥、服务器控制台、重装、换`IP`、终止或其他客户可执行功能；但业务自身的余额、实名、订单状态、二次确认、敏感操作校验和供应商能力门禁仍照常执行，员工身份不得绕过。页面全程醒目标识协助模式、目标客户和剩余时间；后端必须同时保留目标客户与真实员工身份，所有读写审计均记录实际员工、目标客户、协助原因和会话号。启动、每次使用、主动结束和到期保留不可变事件，令牌不得暴露给普通页面参数，过期、退出、撤销或重复使用立即失效。
- 后台客户`360°`不只显示摘要数字，必须提供按需加载、独立分页的完整业务页签：概览统计、个人资料与实名、账户状态和推荐人、余额、账单、资金流水、交易记录、全部订单、产品与服务器、工单、合同、发票、通知记录、运营备注/跟进/黑名单及审计。每个插件只读取自己拥有的数据并通过公开能力或安全页面表面贡献，禁止`core`跨插件查表；任一页签失败只影响该页签并明确说明，不能用假零掩盖故障。管理员从对应页签管理订单、产品、服务器或客户状态时必须复用拥有方正式接口、精确权限、数据范围、业务校验和审计，不能建立旁路。所有长列表使用有界分页、固定表格高度和按需查询，禁止一次加载客户全部历史。
- 后台订单列表必须展示订单号、客户短编号、姓名、手机号、商品信息、服务`IP`、下单时间、支付方式、状态和备注；商品信息作为可伸展业务列，操作列固定在最右侧。跨插件的服务`IP`必须由资源拥有方通过有界公开投影批量贡献，不得逐行请求或直接查资源表；没有服务或尚未分配`IP`时显示清楚的空值。订单状态、支付方式及其他枚举全部本地化，禁止显示原始机器码。
- 客户备注、跟进和黑名单页面不得展示`NTE_`等内部编号、数据库主键或`active`、`planned`等原始状态。黑名单原因由用户可理解的固定选项产生稳定内部代码，不要求用户填写机器码；备注、跟进和黑名单弹窗关闭后必须能立即再次打开并重置到正确状态。
- `core`拥有`idccap`与唯一`secretcap`，`resource`拥有`resourcecap`与版本化 Provider SPI；公开能力必须包含源码 helper、owner-aware descriptor、dispatcher、`hostServices`授权、bridge SDK 和版本检查。源码 Provider 通过`resourcecap/spi`只写后冻结的声明期 registrar 装配：适配器`init`声明版本化工厂，`resource`在`pluginhost.HTTP/Jobs`回调冻结快照、构造最小`ProviderEnv`并显式注入运行服务；禁止运行期全局`Resolve/Get`或修改宿主。`resource`通过`ProviderEnv`向适配器注入受限秘密访问器，禁止各插件重复实现加密。
- 当前宿主已经支持动态插件的 owner-aware descriptor、invoker、WASM 和授权链，但源码插件回调只取得自身`capability.Services`，没有公开的跨插件 owner 服务解析入口。`plugin-owned`能力可以由 owner 在`backend/cap/*`提供类型安全的轻量源码 helper，由消费插件只在`backend/plugin.go`或等价启动装配层显式构造窄 client，并通过业务服务构造函数逐项注入；权威状态必须仍由 owner 插件自己的共享数据库表和幂等围栏保存，消费方不得导入 owner 的`internal`、自行复制状态或在请求路径临时创建服务图。这种显式 helper 路径不要求修改宿主；不能通过该路径安全构造的能力仍须另行评审宿主源码解析增强。在任何情况下都不得用包级全局 service locator、运行期`Resolve/Get`、站内`HTTP`回环或`init`顺序依赖规避边界，也不得把尚未打通的通用解析能力宣称为已完成。
- 指定员工能否成为客服、负责人、审批人或内部通知收件人，不通过修改`lina-core`、读取宿主表、角色名称推断或业务插件自建临时名单解决。新增独立通用源码插件`staff-access`，由其拥有跨插件可复用的员工业务资格、能力编码、作用域、有效期、停用、版本和审计事实，并通过版本化`staffaccesscap`供消费插件显式注入。宿主`Authz`继续只判断当前操作人能否执行按钮动作；`staff-access`结合宿主公开`usercap`的当前可见、启用用户事实和自身权威业务资格，判断目标员工能否被选为某类业务处理人。消费插件仍须校验自己的对象数据范围和部门/队列归属，资格插件不得读取或解释 IDC 工单、账务、资源等业务表，也不得把一个业务域的资格自动扩大到其他能力。插件缺失、停用、版本不兼容、目标用户不可见或停用、资格过期、范围不匹配、版本冲突或查询失败时一律失败关闭。官方`org-core`只负责部门、岗位和组织资料，不承担宿主权限或跨插件员工业务资格，因此不能替代该插件。
- `secretcap`当前只允许通过显式构造函数注入的源码插件 callback accessor 短暂访问明文。宿主普通 owner invocation 只有可记录的请求/响应字节，不具备 confidential、可零化的明文响应通道，因此在完成专门安全设计和独立审查前不得发布动态`secret.access` descriptor、bridge SDK 或通过普通 payload 传递明文；保留动态契约名称不等于运行期可用。
- Provider 契约首版能力矩阵包括开通/查询、启停/重启、暂停/恢复、续期、密码、控制台、重装、变配、换`IP`、快照、备份、安全组、`NAT`、虚拟介质、流量包、终止和上游工单；不支持能力必须明确声明并在界面隐藏或降级到工单。
- 智简魔方快照与备份使用独立能力编码但共用`create/delete/restore`动作模型：创建只允许磁盘编号与受限名称，删除和恢复只允许快照编号；写入前必须从当前实例详情或快照列表只读证明目标唯一归属当前实例并匹配快照/备份类型，缺失、重复、类型不符或畸形响应禁止写入。只有真实上游任务号可证明已受理，普通成功标记、空响应、`401`、超时或连接歧义均保持未知且禁止自动重放。快照/备份配额、对象目录和客户/后台操作入口由资源拥有方单独闭环，不能只凭适配器端点映射开放危险操作。
- `idc-channel`提供只显示一次、哈希保存、可撤销、带作用域和限流的访问令牌，以及商品/库存发布、报价、下单、续费、服务操作、余额/授信、签名`Webhook`和结算对账；首版必须实际交付魔方财务、`V10`与`WHMCS`三个兼容适配器并通过认证、商品/库存/报价、订单创建/查询/取消、余额或信用、续费、服务查询和事件同步最小子集，未验证的其他接口保持关闭。
- 开放`API`订单、付款和服务统一归凭据绑定客户，对方终端客户由对方系统管理；原企业自有与委托双模式决定已由[客户业务与开放 API 规则](76-customer-business-openapi.md)替代。
- 旧魔方名为`invoices`的对象实际是应收账单，新系统统一命名为`billing_invoice`；中国税务电子发票独立命名为`tax_invoice`，两者的接口、页面、状态和表禁止混用。

- 后台创建客户提供两种明确方式。方式一继续发送固定 24 小时有效的激活邀请：同一待激活客户只保留一个有效邀请，重发立即使旧链接失效；管理员不设置、不生成也看不到密码，客户通过链接自行注册或登录后完成绑定。方式二由管理员输入手机号或邮箱作为登录账号并填写初始密码，系统不向该手机号或邮箱发送短信、邮件或激活邀请，直接通过宿主公开用户能力创建独立身份、活动客户主体和客户受众；客户创建成功后立即可以登录，第一次登录必须修改密码。初始密码只允许随本次创建请求进入宿主密码哈希边界，后台不得回显、再次读取、写入日志、审计或普通业务数据库。两种方式都必须填写客户类型、显示名称、国家或地区、界面语言和创建原因；使用手机号时还要从标准选项选择国际区号，国家或地区与国际区号不能要求手填内部代码。若邀请指定已有宿主身份，兑换时必须是该身份本人。已有员工受众、超级管理员或任何有效`idc:admin:*`身份不得自动转为客户，后台只提示使用独立客户账号，不提供隐式或一键转换。
- 当前`LinaPro`源码插件`HTTP`上下文没有投影`bizctxcap.Permissions/IsSuperAdmin`，业务插件不得为此修改宿主或把零值当成普通客户。`IDC`身份门禁采用公开`Authz`安全补偿：检查上下文已有标记、平台管理员、`*:*:*`与唯一完整的`idc:admin:*`权限目录，按宿主上限分批查询且任何错误都拒绝开户；员工永久绑定还必须证明宿主已求值得到 1 至 4 之一的数据范围，零值和不支持值均拒绝。仓库扫描必须以`Go AST`保证每个后台`API`同时位于`backend/api/admin/`并使用`/admin`路由、恰有权限标签，且十个`IDC`插件的后台`API`、菜单/按钮和目录权限集合完全一致。该补偿不得退化为角色名称、角色编号或宿主表查询。
- 查看秘密、修改支付配置、高额调账或退款、批量资源操作、敏感材料导出和权限变更必须要求重新通过宿主登录取得新会话，并用`sessioncap.Current.LoginAt`验证登录新鲜度；不得假定宿主已存在额外 step-up 服务。通过重新登录后签发的证明必须短期、签名、绑定当前用户/商家/会话、操作类型和不可变目标摘要，并以数据库唯一约束原子持久化脱敏 nonce 摘要后单次消费；不得把宿主缓存当成防重放或权限事实来源，因为缓存淘汰、进程重启或后端降级不能恢复证明可用性。刷新旧令牌、跨目标使用和重放均拒绝。签名密钥由每个部署实例的`IDC`商家在自己的后台或部署配置中承担和管理，终端客户不可见。普通确认弹窗不能替代重新认证。后台客户协助会话必须明显标识、限时并全程审计；协助身份可以使用目标客户本人原本可用的功能，但不得绕过这些功能自己的余额、实名、订单状态、重新认证、二次确认、敏感操作和供应商能力门禁，具体会话规则以本文件“完整客户模拟登录”决策为准。
- `@lina/web-customer`必须拥有与`web-antd`相同写法的独立 Vben/Vite`package.json`、TypeScript、`src/`入口、状态、路由、请求、环境、偏好、主题、布局、国际化和构建；官网`SSR/SEO`检查属于各`apps/lina-plugins/website-*/frontend/site/`（2026-10-16独立插件方案替代旧官网目录），不得反向改变客户后台结构。同源路由不得吞掉`/admin`、`/api`、`/x`或`/x-assets`。`idc-portal`后端继续提供官网包管理、品牌内容 API、发布装配、购物车交接和精确认证桥接；宿主密码找回默认路径通过精确`GET /admin/auth/reset-password`保留`token`跳转到`web-customer`的`/auth/reset-password`，不得为此修改宿主。

- 事务`Outbox`与外部业务任务必须分开：`Outbox`承担至少一次事件投递，租约过期且仍有次数时可由幂等消费者重新领取；支付、退款、资源开通等外部写任务一旦超时、断线、进程退出或租约过期，必须把当前尝试和任务冻结为`result_unknown`，先查询外部结果再决定后续，禁止自动重放。通用人工接管只记录处理人和原因并停止自动执行，不提供无证据的“强制成功”或通用直接重试。

- 业务审计写入与查询必须分离。权威状态变更的审计记录必须和业务状态处于同一数据库事务，审计失败时业务一起回滚；敏感查看、拒绝等无状态事件使用先成功落审计再返回数据的短事务。操作者、代操作人、请求与链路信息只能从可信运行上下文解析，业务请求不得自行传入 actor 字段；审计查询必须重新使用公开`Authz`与数据范围，零值、不支持值以及尚不能正确解释的部门/本人范围全部保守拒绝。
