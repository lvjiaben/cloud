# OpenSpec开发流程规则

## 记录门槛

- 新增耐久能力，改变业务、API、数据、权限、模块或长期治理契约时，建立最小必要OpenSpec变更。局部低风险修正、文案、格式和不改变契约的实现修复直接处理，不为了流程创建提案。
- 用户反馈由`lina-feedback`自主分诊：直接修复、补充相关活跃变更、新建变更或仅说明。已有活跃变更不等于必须追加；与本次无关的变更不加载、不修改。
- 有真实业务歧义时先澄清；已授权且范围明确的技术修改持续推进。不是每个任务都必须独立执行一次探索、提案、实施、审查、归档命令。
- 工具可用时使用OpenSpec CLI；工具不可用时保留必要文件并说明未完成CLI校验，不能假称通过。

## 定位与产物

按`context-loading.md`检索和读取。先确定当前任务和目标能力，读取相关完整业务条款、`Requirement`及其`Scenario`；proposal只用于范围、design只用于相关决策背景，其他任务和历史证据仅在存在依赖时读取。

- `contextFiles`和已完成产物依赖是候选路径，不要求整套产物全量读取。同一任务未变化且正文仍可用的上下文可复用。
- 保留当前schema要求的必要产物，内容匹配变更复杂度；简单治理变更用短提案、短设计和可验证任务，禁止无意义模板膨胀。
- 任务一条对应一个可验证结果，同根因的修正合并记录；不反复复制历史汇报、规则全文和所有无影响类别。
- 实施前将当前任务对应到用户完整目标，确定可观察验收结果、关键路径和必要检查；反馈与审查核对目标内遗漏并补齐真实依赖，真正无关的问题另记。新会话交接只携带该任务及有效证据，不搬运整个变更或自动重做已完成项；工具入口见`context-loading.md`。
- 新长期业务确认更新对应偏好主题和受影响规范，任务只链接权威正文，避免形成多份业务真相。
- 大变更保留原任务、验收和证据，用标题/任务ID检索。禁止为节省上下文自动删除已完成记录、修改任务状态或归档。

## 活跃状态与协作

- 仍直接位于`openspec/changes/`下、未移入`archive/`的目录都是活跃变更；CLI显示complete也不等于已归档。
- 修改前查看工作区状态及相关活跃变更，明确本任务文件，避免覆盖其他对话改动。目录清单不要求读取每个变更正文。
- 仅在任务可以独立拆分并明显提升效率时使用subagent；传递目标、路径、边界和必要证据，不复制所有业务正文。小任务或强串行任务直接完成，避免委派成本高于收益。

## 验证与审查

1. 完成前执行与实际变化匹配的测试或治理检查。行为变化按`testing.md`补相应覆盖，纯文档不跑无关运行时测试。
2. OpenSpec产物变更必须执行`openspec validate <change> --strict`。领域强制命令仍按领域规则执行，技能不得自行追加重复门禁。
3. 已通过且仍覆盖当前文件、依赖和运行环境的本次验证可复用；用户复发反馈、并行改动、配置或运行版本变化、失败和覆盖缺口均需补查受影响证据，不在结尾机械重复全套验证。
4. 实现或反馈完成后加载`lina-review`，审查本任务变更；归档前审查完整变更。完成证据必须覆盖当前内容，严重问题阻塞完成。
5. 涉及运行期依赖、构造、启动装配或宿主适配器时，记录DI的owner、创建位置、传递路径与共享实例。影响分析按本次范围说明；无i18n、缓存、数据权限、运行期DI或UI影响可合并一句，不逐项扩写。
6. 只有实现、验证和审查均满足门禁才能将对应任务标为`[x]`。标记完成后出现反证时重新核查并记录相关补修，不沿用旧勾选宣称完成；用户目标内的遗漏持续处理，独立新目标另行分诊。

## 语言、Git和归档

- 新建和更新产物跟随用户语言或明确指定语言，同一变更保持一致；归档和同步基线沿用该规则，不额外强制翻译全部历史文档。
- 目录级README镜像及Markdown格式遵守`documentation.md`。
- 未经用户明确要求，不提交、不推送、不创建PR。
- 归档只在用户明确请求或确认执行归档时进行，先完成完整变更审查和严格校验。任务完成不会自动触发归档或社区提交技能。
