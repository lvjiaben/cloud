# Customer contact authentication

This source-only contract is restricted to `idc-notify`. It stores an encrypted customer contact projection and purpose-separated lookup digests in core-owned storage. It never stores passwords, reads host identity tables, signs tokens, provisions through an authentication lookup, or exposes an account-search API to guests.

Password login resolves an explicit email/phone method to the independent host username. The caller must use the public host login route and re-read the host-signed self profile before returning tokens. Ambiguous, stale, disabled or unowned identities fail closed. Username login retains the host contract. Contact writes refresh the projection within the original authenticated profile transaction. Newly provisioned values come directly from the host account owner; successful customer onboarding refreshes the public self profile.

`POST /x/idc-core/api/v1/admin/account-login/contact-index-refreshes` accepts a fixed-size page. The real staff request must pass IDC customer-update permission and the host public user-query permission. No administrator bearer is retained. Its default response previews role-repair candidates while refreshing derived indexes. Only explicit `repairCustomerAccess=true` repairs active, roleless, platform customers with active `admin_direct` ownership. Existing roles, staff, disabled accounts and restricted customers are excluded. Repair additionally uses the operator's public role-query and batch-assignment permissions and validates the enabled built-in `user` role has self-only scope. New direct accounts receive that same role through `usercap.Create`.

The core identity engine supports only the notification-owned verified-contact provider. Notification recovery verifies a purpose-, account-, contact-, browser- and revision-bound OTP before invoking the published verified-identity login SPI. Recovery tokens remain server-side. The original password write and one-time proof consumption share a transaction. Exact old session IDs are denied through plugin-owned shared storage before response; host revocation can be retried with a separate cleanup-only grant without affecting newly issued sessions.

SQL `149-customer-contact-login.sql` owns the derived index. Model files are generated with the official DAO tool. No host source, private identity storage, signing keys or forged request contexts are used.
