## Context

用户授权独立设计简单、好用的云产品用户中心，明确以插件交付并避免并发冲突。`TDesign React`用于真实表格、表单、弹窗和抽屉，权限、金额、分页及数据保护仍遵循项目规则。

## Goals / Non-Goals

覆盖购买到使用、续费、售后及账户自助的公开客户能力。魔方仅作为导航关系与操作流程参考；费用、归属与授权由业务拥有方判断。此变更不替换共享实例的活动模板。

## Decisions

- 新插件独立锁定依赖、构建前端、打包公开`WASM`资源节和描述符，不导入宿主前端源码。冷灰背景、白色导航、蓝色操作和紧凑表格；窄屏使用抽屉导航、纵向布局与表格横向滚动。
- 仅通过同源公开接口读取或办理客户业务；独立会话存储、单飞刷新、退出后拒绝旧刷新结果。敏感认证与密码查看不自动重放。
- 全量读取启用导航后原子展示。服务、费用和账户按用途分区，组内保留商家名称与顺序；概览、帮助及全部服务作为固定入口。成功空快照保留这些必要入口，不能恢复旧模板菜单；失败显示重试。
- 菜单、销售分类和客户已购服务分别承担导航、选购及服务归属职责。后台中文菜单名必填、英文选填并回退中文；菜单类型已有商品时锁定，商品编辑仍为唯一归属维护入口。
- 金额使用最小货币单位字符串及`BigInt`；真实总数分页与游标分页分别处理。候选项可搜索、翻页；导航分页不截断。
- 购买、配置、购物车、最终核价与下单在模板内完成。写动作遵循版本、能力与幂等契约；付款回跳查询权威结果，续费先报价后确认，密码查看与危险操作显式确认。
- 通知、安全、认证等可选页面依赖实际启用插件。普通通知设置与活动退订使用公开契约；安全通知不能关闭。联系人不获得登录权，原始认证信息不持久化。
- 本插件无业务数据库、服务端缓存和运行期业务`DI`。后端桥接只提供模板描述符；业务`owner`仍为各领域插件。浏览器从公开插件状态建立本次布局的功能上下文。

## Risks / Trade-offs

外部支付到账、供应商动作、认证与开票依赖商家测试环境，本次使用隔离账户、只读真实接口及受控浏览器响应验证。浏览器支持网页、表单和二维码支付；原生应用、微信`JSAPI`及任意第三方页面需要对应适配器。首屏组件包约`230 KB gzip`，构建存在大包提示，业务页面已分路由加载。

## Migration Plan

独立目录构建、`WASI`描述符运行与打包页面预览先行验证。部署时通过已有插件管理流程上传启用，再由管理员选择模板；旧模板可回退。本次不执行共享实例安装和模板切换。

复查真实接口时发现电子合同已由其他任务按最新确认退役，依据偏好主题`14`同步移除本模板合同页面、适配器和签约提示，过滤遗留合同菜单；历史深链接返回账户资料。账户资料导出和注销属于客户自助，仍使用`idc-core`公开接口，不恢复已退役的独立隐私治理工作台。

## 客户头像上传补齐

普通客户没有后台`system:file:upload`权限，原宿主文件上传不能作为个人头像入口。`idc-core`新增`POST /account/customer/avatar-uploads`，由现有客户路由守卫与显式注入的`customeravatar.Service`限制当前有效客户，存储前缀固定为`customer-avatars/`，不接受目标用户或场景参数。通过公开`storagecap.Service`写入插件私有对象，并生成`192 bit`随机键的公开图片地址，再由现有`PUT /user/profile/avatar`更新本人头像。禁止修改宿主或授予后台文件权限。

输入最多`5 MiB`，只接受实际可解码的`PNG/JPEG/WebP`且像素数有限。调用次数固定为一次对象写入，图片访问为一次对象读取，不按数据规模增长；不改数据库、不新增缓存或枚举配置。错误与 API 文案包含中英文。上传失败保留原头像；资料保存后重读并通知顶栏刷新。

实际验证发现`filecap.Detail`对没有后台角色的客户仍拒绝数据范围访问，因此不采用文件中心详情查询，也不伪造管理员上下文。头像图片按既有头像公开 URL 语义，通过`GET /public/customer-avatars/{key}`读取；键仅接受`48`位随机十六进制加允许扩展名，不接受客户编号、其他对象前缀或文件路径，禁止列举。

## 登录凭据改绑的插件方案（2026-10-23）

用户已确认手机号、邮箱属于登录与找回密码凭据，改绑必须先验证旧方式，再验证新值。无可用旧方式走人工核验，首次绑定验证另一项已有方式。此规则替代普通资料直接修改联系方式的旧实现。

当前公开`GET /api/v1/user/profile`能读取本人资料，但插件进程内`usercap.Current/Get`不返回手机号／邮箱，`usercap.Update`属于管理域且无原值比较；普通`PUT /user/profile`也没有凭据版本、验证码证明消费、唯一占用及并发改动保护。经HTTP先读再写不能提供原子验证更新。

此前将缺少专用凭据更新接口直接判定为必须修改宿主的结论过早。用户明确拒绝修改宿主和正常改绑人工审批。本轮验证替代方案：插件从公开本人资料接口取得原值，通知插件复用既有邮箱／短信通道完成旧、新验证；公开全局中间件校验本人、会话、用途、原值、目标值及有效期，在插件事务中一次消费证明并执行原有本人资料路由。宿主源码、私有表和权限身份均不改写。

普通资料继续禁止无证明改写登录联系方式。插件自有账户串行化记录使同账户改绑及后台公开资料修改互斥；事务必须通过真实路由反证证明原路由写入参与同一事务，后续失败不会留下半更新。验证码失败次数必须提交后再返回业务错误，避免事务回滚清零次数。模板只提供自动验证流程和已有工单链接，不新增后台审批。未完成真实验证前不勾选任务`9.4`。

验证码复用通知插件既有短期记录，不保存明文验证码和完整联系方式；新增协调记录属于技术锁状态，不使用软删除。读取和更新的成本固定，不随用户数增长。后台公开更新参与同一账户锁；其他服务未来增加登录凭据写入时必须接入同一保护入口。该保护随插件启用生效，不宣称禁用插件后宿主仍有同等保护。

首次切页数据仅在同一导航、同一登录状态的未提交渲染间复用Promise；提交后移除，导航或身份变化立即隔离，遗留请求完成后最多保留30秒用于垃圾清理。它不缓存已提交的业务结果，不替代服务端权限或后台一致性机制。慢速切页保留原页，180毫秒后出现轻量提示；弹窗仍独立加载，不挂起整页。

### 联合升级计划：2026-10-23

协调方确认联合目标为 `idc-core v0.1.162`、`idc-notify v0.1.8`、`customer-tdesign v0.1.2`。本任务统一维护 core／notify 清单版本并执行其正式升级；官网任务负责冻结后无 overlay 的联合构建及隔离性能验证。notify 的 core 依赖下限提高到 `0.1.162`，用户中心增加通知插件 `>=0.1.8` 依赖，不建立循环依赖。共享实例尚未获切换窗口；安装前读取实际版本，不降级，不以手工 SQL 或改版本字段代替官方升级。

真实隔离验收已完成邮件发码、旧新验证、原宿主资料保存及刷新。插件协调表临时故障触发器在宿主写完后抛错，真实 profile 保持原值，原证明重试后成功，成功后重复使用被拒绝。邮件测试只通过 Go 测试 overlay 将 SMTP 连接重定向到本机 TLS 接收器；无宿主覆盖、无外部投递。正式构建不含此测试 overlay，仍需同一联合产物最终验收。

### 登录标识目标的初次核对（历史状态，已由本轮实现补齐）

用户此前将邮箱／手机称为登录和找回密码方式，需要保留为整体验收目标。源码核对：当前模板 `Auth.tsx` 注册分别收集 `username` 与 `email`，宿主 `auth.Login` 按 `Username` 查询，邮箱找回密码按 `Email` 查询。本轮验证改绑修改联系方式及找回密码使用的邮箱，不修改独立用户名，邮箱／手机作为密码登录别名尚未实现。界面改称“账户联系方式”，避免误导。

现有 `usercap.BatchResolve` 是带当前身份和数据权限的用户查询，不能伪造管理员身份用于匿名登录；`authcap.ExternalLogin` 只接受已验证外部提供者与不可变 subject，Email 仅用于审计，不能当作邮箱密码登录捷径。后续合法实现仍需在插件公开能力内设计并验证，不得匿名提权、直接读取宿主私有表或静默改用户名。此缺口单独列为任务 `9.6`，不抹掉用户目标，也不阻止交付本次已完成的安全改绑。

### 联系方式登录与密码找回实现（2026-10-23，当前）

用户最新确认缺失能力现在实现，短信／邮件凭据由用户稍后配置。这替代上节“尚未实现”的历史状态。当前联合目标为`idc-core v0.1.163`、`idc-notify v0.1.9`、`customer-tdesign v0.1.4`。宿主目录与根`hack/`不修改。

`idc-core`拥有`customerlogincap`和加密联系索引。只索引活动客户绑定及客户主体，邮箱／手机使用目的隔离的HMAC索引、身份快照使用AES-GCM；冲突拒绝自动选择。索引来自带真实令牌的公开本人资料、公开管理分页和公开开户返回值；不读取宿主私有表，不保存管理员令牌或第二份密码。用户名方式保持独立，邮箱／手机先解析同一账户，再由宿主原密码验证并校验真实签发资料。开户、激活、改绑和后台公开资料更新同步可信索引。

旧`admin_direct`开户曾遗漏本人角色。新开户通过公开`usercap.Create`明确赋予启用、key=user、dataScope=4的本人角色；角色异常完整拒绝开户。旧账号同步默认仅预览，只有明确维护动作才为活动平台客户、活动绑定及主体、活动宿主用户且原角色为空的目标补本人角色。索引事务必须先成功提交，之后重新读取真实公开用户和归属，最后执行一次公开批量角色写入。已有角色、员工、冻结、受限及其他来源账户均不补；索引失败绝不先改变权限。每页最多100条，查询和写入批量处理。

通知插件复用现有通道、人机校验、持久化验证码、冷却与发送额度。找回证明绑定账户、联系方式、浏览器、用途、修订和时效，错误次数持久化且凭证一次消费。验证后通过宿主公开已验证身份SPI取得仅留服务器的临时本人会话，原`PUT /user/profile`在通知插件同一事务中写密码并消费证明。临时会话不返回浏览器，失败撤销。

密码保存同一事务捕获真实`sessioncap`会话ID并写插件撤销记录；公开全局守卫仅按真实认证身份及TokenID阻止这些旧登录。宿主清理失败仍立即拒绝旧会话，密码成功保持成功；短期、账户／浏览器／验证号绑定的清理授权只可重试撤销，不可登录或改密码。重新登录的新会话不在旧ID集合中。公开路径按规范化命名空间判断，资源名含public不能绕过。商家停用插件后的宿主原行为不在该插件保证范围内。

前端按用户最新确认使用统一账号输入框，自动识别用户名、邮箱或有效手机号，并且每次提交只验证一次密码，不显示登录方式选项；找回按账户、人机验证码、新密码三步，失败保留必要输入并可重试。未配置通道明确拒绝发码，不出现已发送、倒计时或下一步。原联系方式失效只链接既有工单，不增加人工审批业务。TLS依照用户最新偏好主题19跳过证书验证，但保留TLS加密、最低版本、批准主机端口及禁止重定向等边界。

### 统一账号输入与用户名规则补修（2026-10-23）

本次并入`core v0.1.164`及`customer-tdesign v0.1.5`。用户明确禁止纯数字及邮箱格式用户名，支持的手机号格式也不再占用独立用户名命名空间。注册人机绑定、公开开户与登录统一去除账号首尾空格。前端对唯一账号框做格式分流，复用原三类型密码接口，不增加匿名用户查询或多次密码试探。

`profileguard`在原公开注册、用户新建和用户编辑路由前拒绝新写入的上述用户名；编辑回填历史原值时通过启动期已有`services.Users()`显式注入的公开`usercap.Get`按当前身份及数据权限核对相同目标，仅原值一致才放行。普通昵称、密码保存不增加查询或改变原权限与事务，资料修改未提供用户名时不受新规则影响。后台直接开户原先用邮箱／手机作用户名，改为已有规范化联系方式的稳定`customer_`标识；新开户的宿主手机号与登录索引统一写完整国际号码，客户联系仍保留区号和本地号分段，先拒绝不符合既有登录号码格式的值，不改历史资料。保留本人角色，不改历史名字、索引模式、费用或密码真相。当前公开管理员可见平台9账户中的1个数字／7个邮箱名字均等于本人当前联系方式，未发现跨账户文本碰撞；此核查不扩大到权限范围外数据。

### 首页资源与完整管理反馈（2026-10-23，当前实施）

本节替代早期“全部服务”固定菜单及用户中心自带购物车的设计。首页内部以固定五条读取本人资源明细，产品页面只使用后台定义的分类标签；不会生成“全部服务”导航。列表的备注以独立修订保存，不改变服务生命版本或计费条件；搜索与总数使用相同本人条件及字面关键词。资源状态、IP和系统信息由一次批量本地事实查询装配，无逐行供应商调用。缺少运行观察时区分已生效服务与尚未确认的运行状态。费用只展示当前生效价格记录。该记录可能含初装费或升级后的整期等价价格，不代表最近实收，也不冒充下次续费报价。

备注字段归属`idc-core`现有服务权益聚合，迁移`150`增加备注及独立修订，无独立业务表或缓存。写入行锁、乐观修订和同事务审计；审计仅记录摘要，不保存客户备注原文。精确候选查询与备注接口从本人拥有的服务返回工单不透明关联，不把权益号伪装为工单关联标识。

服务器管理按概览、系统与连接、快照备份、网络安全、日志和费用分区。`idc-resource`拥有原生实例的全部候选、归属、能力、任务、观察和输出；`idc-core`只提供现有权益、收费及当前会话确认。高风险准备证明绑定当前有效登录、客户、服务器、操作、参数及幂等键，不限制最近登录年龄。证明在已有`WithCurrentEntitlement`事务中与策略共享锁、一次消费及资源任务一起提交；业务失败回滚证明，跨会话、跨操作和重放拒绝。

前端先核对设置再显式确认，不将提交视为供应商成功。失败重试保留原请求键和不可变参数，未知结果不自动重发。系统密码和控制台输出仅在当前窗口显式获取，不缓存、不自动重试、不写浏览器存储；关闭立即移除。只把后端验证并返回的安全`HTTPS`地址作为可打开连接。收费快照、备份、流量及规格变更继续接既有报价、结清和生命周期链，不能当作免费资源动作绕过。

本轮联合目标为`idc-core v0.1.164`、`customer-tdesign v0.1.5`，清单由本任务统一维护；资源及供应商插件由原业务对话维护。实际部署官网入口保存在现有公开模板配置，受信客户来源按明确部署来源配置。新产物未完成正式升级及用户入口验收前，不勾选本轮任务或称为全部完成。

## 用户中心菜单两级数据维护

`idc-core`拥有菜单父级、名称、图标、顺序、状态和目标；最多两级，不改变既有商品归属及客户服务权限。后台展示适配保留`useVbenVxeGrid`真实分页，菜单按树形顺序在数据库分页，总数仍计算实际菜单行；缺失父级使用一次有界集合查询附带`parents`上下文，每页最多增加与页大小相同的父节点，不按节点补查。原平面候选读取保持完整分页，避免商品表单漏项。

保存在原审计事务内对当前菜单及目标父级按稳定顺序加行锁，校验父级存在、父级无父级及当前节点无子级，避免并发附加与移位形成第三级。菜单仍是授权商家共享的`tenant_id=0`配置；客户读取仅发布有效启用分支并隔离服务计数，隐藏分支不撤销已有服务访问资格。索引覆盖父级和兄弟顺序，没有新缓存、跨插件私有读取或运行期服务图。

当前`customer-tdesign`模板读取公开菜单投影，按真实父级组织标题式一级与二级链接；后台不保存折叠样式、展开状态或模板布局。一级保留其目标，其他模板可自行决定页面打开与折叠交互。全部图标由现有图标选择器维护；当前模板只把验证后的图标标识渲染为安全的被动图像，失败沿用组件图标，不注入远程标记。
