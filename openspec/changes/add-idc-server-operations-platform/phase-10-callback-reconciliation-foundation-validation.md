# 第十阶段回调对账底座验证记录

## 1. 任务结论

任务`10.6.e.1`已经完成供应商回调、主动查询和人工接管的协议冻结、顺序迁移及加密底座。首次供应商写租约现在会在同一 PostgreSQL 事务创建唯一中央路由；供应商外部流程号不再作为业务请求结果明文保存，而是以独立 AES-GCM 密文和用途隔离 HMAC 绑定到路由，业务请求只保存中央路由号。

本切片仍没有生产回调 HTTP 路由、供应商验签器、供应商客户端、主动查询执行器或人工接管服务。腾讯与诺诺精确验签契约尚未取得可验证证据，因此不能把数据模型完成误报为生产回调可用。

## 2. 数据模型与持久约束

- `supplier_route`一对一绑定写尝试和业务请求，并通过复合外键核对实例、供应商和操作范围。路由保存规范投影、对账状态、单调版本、加密外部流程号及查询时间/租约，不接受第二条尝试或跨实例归属漂移。
- `supplier_evidence`只追加保存回调、主动查询或人工接管的加密原始证据、原始载荷摘要、规范状态、决策码、供应商时间和数据库观察时间。回调事件 HMAC 按供应商唯一，证据不能更新或删除。
- `instance_delivery`按路由和中央版本唯一，固定绑定同一路由的证据，只允许从`pending`单向确认；投递不包含外部流程号、原始回调、签名、主体或平台凭据。
- `supplier_takeover`和证据关联表只允许一至十六条同一路由既有证据、封闭原因、精确版本和平台操作者引用，记录不可更新或删除。
- 路由投影只允许`running/succeeded/failed/result_unknown/manual_takeover`，对账只允许`none/query_required/manual_takeover`。结果未知必须进入查询待办；人工接管的投影和对账状态必须成对出现，并清除查询租约。

## 3. 加密与写租约集成

- `RouteProtector`使用独立 AES-256-GCM 密钥加密外部流程号，并使用另一把用途隔离 HMAC-SHA-256 密钥生成供应商范围内的精确查询摘要；AAD 绑定中央路由号、供应商和密文版本。
- `EvidenceProtector`使用第三把独立 AES-256-GCM 密钥保护有界证据帧；回调帧由最多 256 KiB 原始请求体、最多 16 KiB 已签名头和固定帧开销组成，明文上限为 282624 字节，密文上限为 282652 字节。AAD 绑定证据号、路由号、供应商、来源和密文版本，同时保存明文 SHA-256 用于完整性核对。解密只允许同步回调，返回后清零明文缓冲。
- 供应商写成功观察在服务边界内加密外部流程号，存储层只接收密文和 HMAC；业务请求成功结果指向中央路由号，路由业务投影继续保持`running`并持久化固定的首次回调等待截止点，届时若无终态回调即可由主动查询领取。完全相同结果重放重新加密但以同一 HMAC 精确恢复，改变流程号则冲突。
- 写尝试和路由在首次租约的同一事务创建，响应恢复必须返回相同尝试号和路由号。半开探针超时会在同一事务把尝试、业务请求和路由都标记为结果未知并进入查询待办。

## 5. 规则域与审查

- 架构与插件：所有实现闭环在平台方独立部署的`central-gateway`嵌套模块，未修改宿主、商家后台或 Portal。
- API 与数据权限：未开放新 HTTP 路由；数据库归属从业务请求和写尝试复合外键派生，未来验签器不能按回调自报实例选择数据。
- 数据库与性能：路由、事件去重、查询领取、实例投递和证据列表均有与未来精确查询或稳定排序匹配的唯一/部分索引；单次写租约只新增一条路由，无循环查询或`N+1`。
- 安全：外部流程号与原始供应商证据使用不同密钥、不同 AAD 和不同密文域；数据库、日志、错误和普通结果不保存原文。腾讯/诺诺未核实验签算法仍失败关闭。
- 前端、宿主、缓存与`i18n`：无影响。宿主页既有问题按用户要求不在本任务处理。

`lina-review`复核了复合归属外键、路由全局唯一、状态/对账组合、密文三元组、不可变证据、投递确认边界、接管证据归属、写租约原子路由、探针过期收敛和外部流程号泄露路径。审查中补充了路由/证据/投递的复合所有权约束、数据库状态组合约束、独立证据加密器和成功结果明文消除；最终没有遗留阻断`10.6.e.1`的`P0`、`P1`或`P2`问题。
