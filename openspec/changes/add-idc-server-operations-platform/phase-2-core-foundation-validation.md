# 第二阶段核心数据基础验证记录

## 范围与结论

- 本记录覆盖任务 2.1 和 2.2：新增`idc-core`首批数据库结构、索引、必要字典种子和双语字典资源，并生成、审查对应`DAO/DO/Entity`。
- 本阶段新增 11 张插件自有表，覆盖实例商家、身份受众、客户开户与绑定、客户主体、业务编号、事务`Outbox`、异步任务、任务尝试、幂等记录和业务审计。
- 本阶段没有新增或修改`HTTP API`、缓存、运行时服务、依赖注入或前端页面；业务数据权限执行仍保留给任务 2.3。
- 生产代码仍只位于`apps/lina-plugins/idc-core/`；没有为本阶段修改`apps/lina-core`、`apps/lina-vben`或根`hack`。

## 表与留存边界

| 实体 | 责任与留存语义 |
| --- | --- |
| `merchant_profile` | 单安装实例唯一商家资料；不允许普通删除 |
| `principal_audience` | 宿主身份的`customer/staff`互斥受众；通过撤销状态保留历史 |
| `customer_subject` | 个人或企业客户主体；符合条件的注销执行匿名化，不做普通物理删除 |
| `customer_onboarding_intent` | 短期、单次开户意图；令牌、浏览器随机数、用户名和联系方式只保存摘要 |
| `customer_identity_binding` | 宿主身份与客户主体的一对一绑定；通过撤销状态保留历史 |
| `business_number` | 随机、不透明业务编号的幂等保留账簿；分配后不回收复用 |
| `outbox_event` | 与权威业务状态同事务写入的事件；发布、死信或结果未知后按策略归档 |
| `async_task` | 异步业务任务、租约、重试和人工接管状态；按业务证据策略留存 |
| `async_task_attempt` | 每次执行尝试独立留痕；不允许业务删除 |
| `idempotency_record` | 调用方范围内的请求指纹和脱敏响应；达到期限后受控清理 |
| `business_audit_event` | 追加式脱敏业务审计证据；不允许普通删除 |

所有表名均使用完整前缀`plugin_idc_core_`。所有表均包含`tenant_id INT NOT NULL DEFAULT 0`和数据库`CHECK (tenant_id = 0)`，与一个安装实例只服务一个`IDC`商家的产品边界一致。

首批表没有统一增加`deleted_at`。客户主体采用状态和`anonymized_at`表达受控注销；身份绑定采用撤销状态；开户意图、幂等记录、`Outbox`和任务采用状态、到期时间或归档策略；任务尝试、业务编号和审计记录保留为历史证据。该选择落实了按记录类型分别保留、匿名化、归档或删除的设计，避免用统一软删除掩盖资金、资源和审计证据。完整自动处置矩阵仍由任务 18.10 交付。

`001-core-foundation.sql`只包含`DDL`和系统运行必需的字典`Seed DML`，没有演示或测试`Mock`数据。自增主键全部由`GENERATED ALWAYS AS IDENTITY`维护，种子写入没有显式指定`id`。由于该插件为内建业务拥有方，且表中包含不可普通删除的历史证据，本阶段没有提供破坏性的卸载`DROP SQL`。

## 身份、数据权限与安全边界

- `principal_audience.sys_user_id`具有唯一约束，一个宿主登录身份不能同时成为客户和员工。宿主身份只保存编号，不直接查询宿主表，也不建立跨插件或宿主数据库外键。
- 客户身份绑定同时约束`sys_user_id`和`customer_no`唯一，首版保持一个客户主体对应一个登录身份。绑定来源区分门户开户、管理员邀请和迁移。
- 开户意图只保存`SHA-256`摘要和必要状态；明文令牌、验证码、密码、联系方式与浏览器随机数不进入该表。返回路径必须在后续服务层按同源白名单验证。
- 业务编号保留账簿的唯一范围包含编号类型、`reservation_scope_digest`和`idempotency_key_digest`；服务层必须以规范化调用方或命令范围生成前者，并使用密码学安全随机源生成编号。幂等记录的唯一范围包含`scope`、`caller_scope_digest`和`idempotency_key_digest`，防止不同客户或渠道之间重放同一幂等键。
- 异步任务的唯一范围包含业务对象类型和编号，允许不同客户使用相同客户端幂等键，同时拒绝同一业务对象的重复任务；独立`customer_no`是在创建事务中验证并固定的客户归属投影，供任务列表在数据库查询阶段执行权限过滤，客户无关的系统任务保持为空。
- 审计表分别保留有效操作者、实际代操作人、操作者代表的客户、被影响客户主体、目标、操作、结果、风险、请求和关联编号；员工、系统或外部调用方替客户执行操作时也能直接按被影响客户过滤，快照字段明确要求写入前脱敏。
- 本阶段只建立结构约束，没有声称已经完成运行时数据权限。客户所有权、员工权限、对象不可见语义和开户兑换门禁将在任务 2.3、3.3 与 3.10 中实现并测试。

## 查询与索引设计

- 客户列表按`tenant_id + status_code + created_at + id`稳定分页，并提供客户类型和状态组合索引。
- 开户意图按状态与到期时间领取，按联系方式摘要和宿主注册身份定位；可空宿主身份使用部分索引。
- `Outbox`和异步任务均按`tenant_id + status_code + available_at + id`领取，租约、外部编号和关联编号使用部分索引；业务对象历史使用类型、编号和时间索引，客户任务使用独立客户归属部分索引。
- 幂等记录使用调用方范围唯一约束，并提供到期清理和业务资源反查索引。
- 业务审计提供时间线、目标、有效操作者、实际代操作人、操作者客户、被影响客户、关联编号、操作、结果和风险索引；可空或空字符串字段使用部分索引，避免低价值索引项。
- 客户编号、商家编号、开户编号、绑定编号、事件编号、任务编号和审计编号均有稳定唯一约束，可用于集合化批量读取和跨插件不透明编号关联，不要求应用层逐行查询。

## 字典与国际化

- 新增 14 组宿主字典类型和 54 个稳定字典值，覆盖受众、绑定、客户、开户、`Outbox`、任务、幂等和审计状态。
- `en-US/dict.json`和`zh-CN/dict.json`的字典类型与值完全一致；英文资源作为源内容，中文资源覆盖默认语言。
- 宿主默认`zh-CN`会保留数据库内可编辑标签，因此种子名称、标签和备注使用中文；切换`en-US`时由插件资源按`dict.<type>.<value>.label`等稳定键投影英文。
- 本阶段没有新增`API`文档元数据或前端静态文案，因此没有`apidoc`和页面语言包影响。

## DAO、DO 与实体生成

- `hack/config.yaml`显式列出 11 张完整物理表，`removePrefix`为`plugin_idc_core_`，`importPrefix`为插件后端自身`internal`路径；生成范围没有包含宿主表或其他插件表。
- Windows 环境没有 GNU `make`，因此使用插件`make dao`目标实际转发的同一项目命令`make.cmd dao dir=apps/lina-plugins/idc-core/backend`。生成器产出 11 个公开`DAO`、11 个内部`DAO`、11 个`DO`和 11 个`Entity`，没有手写或二次编辑生成文件。
- 代码生成使用独立本地数据库`linapro_idc_codegen`。该库只接收宿主的 29 张表结构以及本插件迁移，不复制现有库的任何业务数据；迁移双次执行后 11 张插件表仍为 0 行，现有开发业务库未被修改。
- PostgreSQL 目录中的 196 个插件字段与 11 个`Entity`的 196 个字段逐一匹配：`BIGINT`映射为`int64`，宿主用户编号等`INTEGER`映射为`int`，`BOOLEAN`映射为`bool`，字符、文本和`JSONB`映射为`string`，时间字段映射为`*time.Time`，没有类型遗漏或偏差。
- 11 个内部`DAO`均保留完整物理表名，全部生成层均不存在`DeletedAt`或`deleted_at`。第二次执行相同生成命令后 45 个现有 Go 文件的`SHA-256`摘要字节级不变，`gofmt -d`输出为空。
- 生成层只提供本插件表的数据访问对象，没有增加跨插件导入、跨表访问、运行时数据权限声明或循环装配逻辑；客户归属字段和索引已为后续数据库侧过滤与集合化查询保留入口。

## 数据库验证

在本地开发`PostgreSQL`连接中，以同一个`psql`会话执行`BEGIN`，连续加载两次`001-core-foundation.sql`，执行约束断言和目录统计后`ROLLBACK`。整个验证事务没有持久化到现有数据库。

| 验证 | 结果 |
| --- | --- |
| 第一次加载迁移 | 创建 11 张表、14 个字典类型和 54 个字典值 |
| 第二次加载相同迁移 | 表与索引安全跳过，字典分别写入 0 行 |
| 表前缀与租户约束 | 11 张表全部使用完整前缀，目录中存在 11 个租户`CHECK` |
| 非零租户写入 | 测试写入被`check_violation`拒绝 |
| 任务幂等范围 | 不同业务对象的相同幂等摘要成功写入 2 行；同一对象重复写入被`unique_violation`拒绝 |
| 业务编号幂等范围 | 不同保留范围的相同幂等摘要成功写入 2 行；同一范围重复写入被`unique_violation`拒绝 |
| 受影响客户审计 | 员工操作者的客户编号保持为空，同时可用独立`customer_no`检索到被影响客户记录 |
| 索引目录 | 11 张表共有 61 个索引，包含主键和唯一约束自动索引 |
| 事务收尾 | 全部测试数据和结构执行`ROLLBACK`，现有数据库未改变 |

静态检查同时确认：11 张表都有完整前缀和租户约束；83 个显式约束或索引名称最长 48 个字符；14 组、54 个字典值与中英文资源完全匹配；不存在`deleted_at`、数据库外键、`ON DUPLICATE KEY UPDATE`或种子显式自增`id`写入。
