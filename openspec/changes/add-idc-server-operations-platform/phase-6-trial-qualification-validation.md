# 第六阶段服务器试用资格验证记录

> **`FB-52`失效声明：**本记录把试用资格绑定到逐台服务器履约单元，原结论已经失效，不能作为当前通用试用完成证据。试用应按“客户 + 商品”和订单项购买数量占用、消费、释放或过期，后续任务粒度由冻结插件契约决定；服务器只是其中一个插件示例。下文仅用于删除旧表、旧字段、旧测试和开发数据迁移对账，不保留兼容层。

## 范围与完成边界

本记录覆盖任务`6.12.c`：按客户与商品累计的服务器试用资格、最终报价权威次数、结账占用、逐台服务器权益、取消释放、统一财务结清消费，以及并发防重和财务隔离。

本切片只建立试用的财务资格和`financially_settled`权威事实，不直接推进库存、履约单元或资源状态。阶段`8.2.b`仍负责幂等消费统一事件并创建业务操作，因此父任务`6.12`继续保持未完成。

## 资格与报价语义

- 试用范围固定为`客户 + 商品`，不包含商品版本；商品发布新版本、调整配置或切换资源池都不会重置已占用或已消费次数。
- 计费规则`trial_quantity`解释为该客户对该商品可试用的服务器台数上限。最终客户报价和后台协助报价以一次有界集合查询读取当前`held + consumed`投影，并冻结`trial_limit_quantity`与`prior_trial_uses`到报价和订单项。
- 匿名公开配置只声明`requires_customer_context`，不假定历史次数；游客购物车不能加入试用项。整张试用订单只允许试用项目，安装费、周期费、折扣、税额和应付金额必须全部为零，禁止与付费项目混装。
- 最终报价不是并发授权。结账事务在创建订单、账单和逐台履约单元后，按商品稳定排序锁定权威资格范围，重新验证`held + consumed + 本次台数 <= 冻结上限`。

## 结账、取消与统一结清

- 每个服务器履约单元创建一个唯一`held`试用权益；客户商品范围同步增加持有台数，并追加一条包含完整前后投影和不可变摘要的`hold`变动。
- 统一结清重新锁定范围和全部权益，核对当前有效个人或企业实名、订单账单归属、冻结商品版本、计费规则、逐台履约身份、持有期限、资格变动和摘要。全部成立时，把权益转为`consumed`、范围持有数转入消费数、追加`consume`变动，并与唯一结清头、试用来源证据和事务 Outbox 原子提交。
- 客户取消待付款订单时把仍持有的权益转为`released`；因付款期限到期取消时转为`expired`。两者都归还持有数量并保留追加式历史，已经消费的次数不能释放。
- 后台协助试用订单使用目标客户的同一资格范围；审批后的零金额试用结账自动请求统一结清，员工不能直接写订单已支付或履约状态。

## 财务隔离与数据完整性

- 试用结清不创建渠道交易、支付分配、账本交易、余额快照或信用敞口，只记录`basis=trial`的结清事实和受摘要保护的试用来源。
- 迁移`036-trial-qualification.sql`新增客户商品资格投影、逐台权益和追加式变动链，并为报价与订单项增加试用上限和历史次数快照。迁移只有 DDL，没有 Seed 或 Mock 数据。
- PostgreSQL 延迟约束在事务提交时核对资格范围的`held/consumed/version`与逐台权益、最新变动完全闭合。资格范围只能连续推进版本；权益只允许从`held`单向进入`consumed/released/expired`；变动历史禁止更新或删除。
- 资格事实只保存内部不透明编号和身份认证证据摘要，不复制姓名、证件号、营业执照、人脸或认证供应商原始载荷。迁移可重复执行，独立 schema 连续执行两次结果一致；孤立范围或不闭合投影在提交时被数据库拒绝。

## 性能与并发边界

- 报价按本次商品集合一次聚合读取资格使用量，不按商品逐行查询；没有 Provider 或其他外部调用。
- 结账一次集合读取订单履约身份，一次批量补齐缺失资格范围，按商品号稳定锁行，再批量写权益、范围投影和变动；单订单继续受既有购物车和最多`1000`个履约单元硬上限约束。
- 取消和结清均先集合读取商品范围，再按同一稳定顺序锁资格范围及有界权益，避免跨商品锁序反转。摘要集合在计算前排序，使多台服务器和不同查询顺序得到确定性证据。
- 两份独立批准的后台试用报价并发结账时，数据库范围锁只允许一笔占用剩余资格；失败事务不留下订单、账单、权益、范围变动或部分占用。

## 审查中发现并修复的问题

1. 最初试用报价只具备规则配置，没有客户历史次数的权威输入，匿名上下文可能把未知次数当成零。现匿名结果明确要求客户上下文；客户和后台报价统一批量读取资格投影，最终报价缺少权威次数时失败关闭。
2. 初始结账设计只按订单项占用一次资格，无法表达同一配置购买多台服务器。现每个履约单元都有唯一权益，客户商品范围按服务器台数守恒，真实 PostgreSQL 用两台服务器覆盖该语义。
3. 权益摘要集合原先依赖调用方查询顺序；结账按行号和单元序号读取，结清按履约编号读取，多台服务器可能产生不同顺序。共享摘要函数现复制并排序权益和变动摘要后再计算，避免把数据库返回顺序当成证据语义。
4. 两个分别生成的有效试用报价都可能看到同一历史次数。现报价只负责冻结说明，结账按客户商品范围行锁重新判定；20 轮真实并发回归证明只能有一笔订单和结清事实成功。

## 影响判断

- API 与数据权限：无新增 HTTP API、路由、权限或数据权限入口；客户所有权继续由当前活动主体派生，后台协助流程继续使用既有目标客户审批边界。
- 国际化：无新增用户可见运行时文案、API 文档或插件清单文本，本切片没有插件国际化资源变化。
- 前端与 E2E：无页面或交互变化；试用商品和结账 UI 由后续 Portal 交付，不能用前端状态代替结账资格锁。
- 缓存：无影响。试用资格每次从本地 PostgreSQL 权威投影读取，不新增缓存或失效协议。
- 外部系统：不调用支付渠道、Provider 或实名供应商；结清只读取本地已验证身份投影。
