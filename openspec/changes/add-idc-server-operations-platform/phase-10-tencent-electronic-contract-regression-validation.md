# 第十阶段腾讯电子签整组回归验证记录

## 结论

任务`10.8.g`要求的整组回归证据已经补齐。腾讯官方客户端假服务契约、每套安装运行门禁、双语后台开通向导、模板目录与编辑、签署方、可选与强制合同、企业自动签和客户合同后端契约均通过对应单元测试、真实 PostgreSQL、前端类型检查、生产构建和真实 Chrome 回归。

`10.8.a`至`10.8.g`已经全部完成，因此父任务`10.8`可以精确勾选。该结论不是用脚手架、旧 Portal 或未触网假服务冒充完成：假服务只证明腾讯请求映射和失败保护；本地业务还分别经过真实 PostgreSQL、三个前端所有者的构建、三个真实浏览器用例组、双语检查、插件治理和 Windows/Linux 安装包验证。

本地验证没有调用购买方腾讯生产账号，也不声称替购买方完成正式腾讯验收。生产启用时仍由每套安装使用自己的腾讯账号、应用、主体、权限、白名单和套餐逐项通过运行门禁；用户已经确认这一对接由购买方自行完成。缺少能力时只关闭当前安装的对应功能，不回退软件提供方中央服务。

客户“我的合同”、订单详情签署按钮和返回后页面状态仍由`10.12`直接在`@lina/web-customer`实现。本项没有进入第十五阶段，也没有向旧 Portal 或`web-antd`写入 IDC 业务源码。

## 安装包清单修复

整组复核发现，运行时已经静态注册腾讯本地业务路由，但发布工具仍保留`10.8.a`早期的`businessRoutesEnabled=false`。这会让安装包清单与真实运行能力冲突，因此已经把发布清单和对应测试改为`true`。

修复后真实构建并保留两套验证包：

- `temp/20260817/phase10-10.8g-windows-amd64`
- `temp/20260817/phase10-10.8g-linux-amd64`

两套清单各有`28`个文件，逐文件`SHA-256`全部匹配，并同时声明`supplierClientsIncluded=true`、`businessRoutesEnabled=true`、`productPackageRequired=true`和`localInstallationOnly=true`。这里的业务路由是购买方安装内的腾讯路由；诺诺生产能力仍关闭，不存在中央回退。

发布工具是跨平台 Go 实现，没有新增 PowerShell、Shell 或平台专属默认入口。对应发布工具测试、Windows/amd64 和 Linux/amd64 真实构建均通过。
