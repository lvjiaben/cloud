# 第五阶段首次付款实名门禁验证记录

## 完成范围

本轮完成任务`5.6`中由`idc-core`拥有的付款准备领域底座：

- 新增客户所有的可恢复付款准备上下文，同一客户同一订单使用确定性上下文号和数据库唯一约束，重复准备或认证完成后的恢复不会创建第二份商业事实。
- 每次准备与恢复都重新锁定并读取当前订单、待付账单、客户主体和对应的个人或企业认证投影。上下文中的认证案例号、状态与版本只是最近评估证据，历史`ready`不构成永久授权。
- 付款状态明确区分等待实名、等待独立订单审核、可以付款、已过期、已取消和已关闭；认证过期或撤销、订单终态、账单资金状态或支付分配变化都会重新失败关闭。
- 普通个人服务器订单不查询或等待可选合同。`requires_contract`仅作为后续履约信息返回，不参与付款准备决定；合同强制签署及其拒签补偿仍由阶段`10`负责。

本轮没有新增客户门户`HTTP`接口或页面；这些由任务`5.7`装配。本轮也没有创建真实支付尝试或调用支付渠道；阶段`7.1`的支付 owner 在创建渠道支付前仍必须调用同一权威重检，不能缓存本轮返回的`ready`。

## 数据库与敏感信息边界

`025-commerce-payment-identity-gate.sql`新增唯一付款准备上下文表、客户/状态与到期索引、状态和原因字典。迁移可重复执行，标准 DAO/DO/Entity 已重新生成，插件版本提升到`v0.1.38`。

上下文只保存客户、订单、账单、客户类型、最近认证状态、认证案例不透明引用和版本，不复制身份证件、人脸、生物识别材料、营业执照、企业资料或供应商原始载荷。商业身份、首次请求时间和订单截止时间由数据库触发器保护为不可修改；`ready`必须同时具备已认证状态、非空案例号、正版本和准备时间，其余状态必须清除准备时间。

事务锁序固定为订单、既有付款上下文、账单、客户主体、个人或企业认证，再读取账单支付分配。恢复入口第一次只按“上下文号 + 当前客户”读取订单号，第二个评估事务仍从订单锁开始，因此不会形成与首次准备相反的锁序。不存在与未授权目标统一返回不可访问，避免通过订单号或上下文号探测其他客户数据。

## 放行条件与恢复语义

只有当前活动客户自己的订单满足以下全部条件时才返回可以付款：

- 订单仍为`pending_payment`且未过付款截止时间；`manual_review`保持独立待审；
- 订单和账单客户、币种、总额及付款截止时间完全一致；
- 订单总额为正，账单仍待付，实收、可退、已退款和支付分配均为零；
- 当前个人或企业认证为`verified`，案例号、版本和认证时间完整，且认证有效期未过。

认证完成后复用同一上下文恢复精确订单、账单、币种、金额和截止时间；认证被撤销后再次恢复会把状态改回等待实名并清除`ready_at`。合同要求只进入显示安全投影，决策函数不读取合同状态或调用合规供应商。

3. 真实事务同时覆盖企业认证、订单取消、风控人工审核独立性和可选合同不阻塞付款。过期与非待付关闭状态的优先级由不依赖数据库时间篡改的纯决策单元测试覆盖。

## 复审结论

本轮按`lina-review`检查了客户所有权、存在性隐藏、固定锁序、并发幂等、数据库权威时间、认证撤销、账单资金前置条件、独立风控、合同边界、敏感数据最小化、迁移约束、查询投影和同步外部调用。审查期间修正了测试夹具对不可变账单的错误变更方式，并补充类型化空依赖防御以及已过期/已关闭决策测试；修复后的真实 PostgreSQL、全量测试、lint、插件治理、严格规范与正式构建均通过。当前没有遗留的严重或高优先级实现问题。

## 规则影响记录

- 架构与插件：生产逻辑闭环在`idc-core`，没有修改`lina-core`、`lina-vben`、根构建工具或其他业务插件；客户 HTTP 装配明确留给`5.7`，支付渠道副作用明确留给`7.1`。
- 数据权限：所有者只从当前活动客户主体取得；订单号和上下文号不能替代客户所有权，不存在和越权目标使用同一失败语义。
- 数据库：新增幂等迁移、约束、索引、字典与生成模型；金额继续使用整数最小货币单位，截止和评估时间使用 PostgreSQL 权威时间，不使用软删除。
- 接口与前端：本轮没有新增`HTTP API`、页面、菜单或用户可观察前端流程，因此没有`Controller`生成、`Chrome`实测或`E2E`影响。
- `i18n`：新增状态、原因和业务错误均有中英文资源；仓库级既有宿主缺键仍是唯一阻断。
- 缓存与外部系统：付款准备永远读取本地权威数据库，不使用缓存，不访问实名供应商、支付渠道、Provider、合同、通知或 AI。
- Git：未执行暂存、提交、推送或创建 PR。
