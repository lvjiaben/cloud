# 第十阶段合同重新发起与解除后端验证记录

## 1. 任务结论

任务`10.9.c`已完成。当前安装的有权后台人员可以使用相互独立的精确权限重新发起合同或解除已完成合同：

- 合同内容、金额、模板和签署人不变时，保留原不可变合同，追加新的`reissue`流程，并从本次重新发起时间开始重新计算固定`7`天签署期。
- 任一冻结内容变化时，先创建新的不可变合同版本和只追加替代关系，只返回预览；管理员检查预览后，再通过独立命令提交腾讯。
- 解除只接受已完成合同、必填解除原因、四项可选约定、页面明确二次确认和原合同签署人；首版没有替换签署人入口，也不要求最近`5`分钟重新完整登录。
- 解除生效时间和解除文件不由请求提交，只等待腾讯权威结果。原合同、原签署流程和全部历史均保留。

本任务只实现后端契约，没有新增后台或客户页面。合同文件归档仍属于`10.9.d`，整组回归仍属于`10.9.e`，后台和客户页面仍属于`10.12`，浏览器验收仍属于`10.17`。因此`10.9`父任务保持未完成。

## 2. 已冻结的业务契约

| 场景 | 当前结果 |
|---|---|
| 原合同内容完全不变 | 原合同追加`reissue`流程，不复制合同 |
| 内容、金额、模板或签署人变化 | 新建不可变合同版本和替代关系，先预览、后提交 |
| 重新发起有效期 | 从本次创建时间开始固定`7`天 |
| 解除权限 | `idc:admin:compliance:contract:terminate` |
| 重新发起权限 | `idc:admin:compliance:contract:reissue` |
| 解除签署人 | 首版固定沿用原合同签署人，不允许替换 |
| 解除填写项 | 原因必填；保留条款、费用处理、其他事项处理、其他约定选填 |
| 解除确认 | 管理员检查完整内容后明确二次确认 |
| 最近完整登录 | 解除不要求最近`5`分钟重新完整登录 |
| 生效时间和文件 | 只接受腾讯后续权威结果 |

腾讯官方`ChannelCreateReleaseFlow`说明原合同必须完成签署，默认示例沿用原流程签署人，并明确原合同个人参与方不得换成第三方个人。本项目首版按用户确认采用更严格边界：任何签署人都不允许替换，只提交原腾讯流程编号和解除约定，不向腾讯提交替换签署人。[腾讯电子签发起解除协议官方文档](https://qian.tencent.com/developers/partnerApis/startFlows/ChannelCreateReleaseFlow/)

## 3. 实现范围

### 3.1 管理接口

- `POST /admin/compliance/electronic-contracts/{contractNo}/replacement-previews`只创建本地替代版本和预览，不调用腾讯。
- `POST /admin/compliance/electronic-contracts/{contractNo}/reissues`只提交已经存在并经过检查的合同版本，或为原内容不变的合同追加新流程。
- `POST /admin/compliance/electronic-contracts/{contractNo}/terminations`要求合同版本匹配、原因有效且`confirmed=true`，然后追加解除流程。
- 三个公开服务入口统一返回结构化业务错误，数据库、加密或本地网关原始错误不会直接成为用户提示。

### 3.2 本地独立运行

- 合规插件通过安装时创建并共享的本地网关客户端调用当前安装的固定签名路由；没有中央业务网关或软件提供方业务服务回退。
- 本地网关使用启动时冻结的腾讯客户端、购买方自有腾讯配置、本地供应商主体和既有写保护，新增独立能力`flow.release`。
- 解除调用腾讯官方 SDK 的`ChannelCreateReleaseFlowWithContext`，请求只含原流程编号和解除约定。没有替换签署人、客户端指定生效时间、自定义端点或中央账号。
- 幂等号、请求摘要、腾讯路由号和加密请求快照均由当前安装保存。结果不明确时禁止盲目重发。

## 4. 数据、权限与性能边界

- 管理接口元数据和服务层分别校验精确权限，并以目标合同号作为授权对象；直接请求不能绕过页面隐藏。
- 当前插件固定单安装、单商家数据边界，`tenant_id`只能为`0`。本任务没有新增列表、导出或聚合接口，也没有逐行远程查询。
- 迁移`017-contract-reissue-termination.sql`删除原来“一订单只能有一个合同”的唯一索引，改为支持历史版本的有序索引，并新增不可变替代关系表。
- 替代关系对旧合同、新合同、替代编号和幂等摘要建立唯一围栏；更新或删除由数据库触发器拒绝，外键禁止删除仍在历史链中的合同。
- 合同创建继续使用订单级数据库事务锁，取消唯一索引不会放开并发重复创建。
- 迁移只有幂等`DDL`，没有`Seed DML`、`Mock`数据、软删除或手写自增主键。真实 PostgreSQL 测试逐个迁移连续执行两次，并验证替代历史不能修改或删除。
- DAO、DO 和 Entity 由项目代码生成入口维护；本任务新增`contract_replacement`生成模型，没有手改生成器声明。

## 5. 依赖来源检查

- owner：不可变合同、替代关系、流程和操作审计由`idc-compliance`后端拥有；腾讯客户端、供应商主体、写保护和本地签名路由由同一插件交付的`central-gateway`组件拥有。
- 创建位置：`backend/internal/composition/contract.go`在插件启动装配时创建一份合同服务，并注入共享数据库、核心合同快照能力、密封存储、权限校验器、模板目录、客户读取器、生命周期服务和本地网关客户端。
- 传递路径：同一合同服务实例注入管理控制器和客户控制器；请求处理过程中不重新创建数据库、加密管理器或本地网关客户端。
- 本地网关创建位置：`central-gateway/internal/app/local_runtime.go`在进程启动时创建一次腾讯客户端，并同时交给合同写入、主动查询、回调和主体绑定服务复用。
- 缓存一致性：本任务没有新增进程内缓存；合同版本、幂等、替代关系、流程状态和权限结果均以数据库或宿主权威服务为准。
