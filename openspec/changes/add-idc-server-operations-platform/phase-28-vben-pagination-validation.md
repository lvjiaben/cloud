## 已确认原因

- 两端现有 Vben 适配器已经提供每页`10`条和`[10,20,50,100]`候选，官方封装也提供完整布局；部分业务页显式禁用了分页，再在外部手写按钮。
- 客户工单接口只返回`nextCursor`，没有总数及随机页查询；客户服务器、授信申请和授信账单也只读取第一段数据，不能把这部分长度说成总数。
- 部分详情表使用已经完整取得的有界明细集合，必须与大规模业务列表区分；不能因为分页外观统一而新增全量网络请求。

## 首批实现边界

1. 工单列表：在所属`idc-core`工单查询上提供可选数字页及准确总数，保持原客户自隔离、员工数据权限、筛选、排序和批量关联装配；客户工单页使用官方分页及原 Vben 搜索。
2. 工单总数在游标条件之前使用同一业务筛选和权限条件计算，不能暴露其他客户、内部工单或其他员工范围；每次固定增加一次计数，不逐行查询。
3. 数字页查询在数据库侧执行有界`LIMIT/OFFSET`，单页最多一百条；无效页及混合游标输入明确拒绝，超出真实末页返回空页及准确总数，不遍历全部游标。
4. 搜索与每页条数变更回到第一页；加载失败保留已确认行和页码，重试使用最近失败参数。
5. 其余表格先按真实接口分类再逐项接入，清单和结果持续追加，不以公共分页外壳替换宣称所有页面完成。
6. 后台订单：复用订单拥有方的授权后查询和原排序，新增可选数字页及真实总数；计数和当前页在只读一致快照执行，不改变订单详情、付款、客户卡片列表或合同流程。客户筛选及客户自有范围仍来自原正式入口，关联客户、商品和支付方式继续按页批量装配。

## 验证要求

需要覆盖真实 PostgreSQL 下的页码定位、总数、字面量搜索、客户与员工隔离，以及 Chrome 下的完整分页显示、改变每页条数、直接跳页、空页、失败恢复和灰白区域。API 变更执行所属包编译、代码生成核对、`make lint`和`i18n.check`；不重置本地数据库，不调用真实供应商，不提交或推送。

## 综合回归发现的请求状态丢失

五十三项最终回归之前的一轮五十二项结果为四十七通过、五失败。其中订单、渠道、客户工单的三项失败来自同一原因：正式`RequestClient.request()`在失败时只抛响应正文，丢失真实`HTTP`状态；因此页面虽有拒绝清空逻辑，却不能识别`403`。另两项信用用例由测试定位包含匹配误中多个编号引起，已改为单元格完整文本匹配，不削弱业务断言。

三个拥有方私有帮助函数继续复用原请求客户端、认证刷新和成功响应处理，在每次请求与刷新重放时单独记录实际传输状态。网络失败不继承上次`401`，不以业务`code`冒充传输状态，不增加重试，不修改共享错误对象。订单只改`commerceOrders`列表调用；渠道只替换本页请求适配；客户侧限于当前信用调用和工单列表。临时`503`保留已确认页，明确`401/403`清空旧授权数据，原有迟到响应隔离断言保留。

订单新增`frontend/pages/commerce-request.ts`及`frontend/tests/commerce-request.test.ts`，十三项真实客户端和官方认证拦截器测试通过，耗时`19ms`；正式订单页类型检查与新帮助函数、测试文件的显式类型检查均通过。测试首次运行因进程工作目录和外部依赖解析不一致失败，最终以插件前端为工作目录、直接调用已安装的宿主测试运行器解决，没有安装新依赖。
