# 第二阶段身份受众验证记录

## 范围与结论

- 本记录覆盖任务 2.3：单商家默认租户、互斥`customer/staff`受众、员工首次授权绑定、客户开户意图兑换，以及十个`IDC`插件的后台权限命名与目录治理。
- `idc-core`新增内部`principal`领域服务和数据库持久化实现；普通身份查询保持只读，只有显式员工绑定或开户兑换命令可以写入。
- 本阶段没有暴露`HTTP API`、控制器或页面。开户意图创建、人机校验、频控、联系方式验证码、浏览器随机数随请求核验、开户状态接口、`POST /account/onboarding/redeem`和对应`E2E`仍由任务 3.10 交付。
- 本阶段没有交付跨插件`idccap`调度器或其他九个插件的员工中间件；这些能力仍属于任务 2.5，并将在各插件首个后台接口出现时接入。
- 生产代码只位于`apps/lina-plugins/idc-core/`，没有修改`apps/lina-core`、`apps/lina-vben`、根`hack`或其他插件。

## 单商家身份边界

- 所有服务入口从宿主`bizctxcap.Service.Current(ctx)`取得当前身份，并要求`user_id > 0`与`tenant_id = 0`；非默认租户在任何插件数据访问前拒绝。
- 一个`sys_user_id`只能有一条`principal_audience`。服务只接受`customer`或`staff`，不会按角色名称、角色编号、用户名或宿主表记录推断受众。
- `Current`固定读取受众、客户身份绑定和对应客户主体，只有受众与绑定同时不存在时才返回未开户；孤立绑定、客户受众缺少绑定或主体、状态不一致、员工受众残留客户绑定、未知客户类型或未知生命周期都返回稳定的不一致错误。
- `EnsureCurrentStaff`只在授权判断成功且宿主已求值得到 1 至 4 之一的有效数据范围后进入事务；数据范围零值与不支持标记均拒绝。事务锁定受众与客户绑定，拒绝客户、撤销受众和孤立客户绑定；并发的相同员工绑定通过唯一约束与重新读取收敛到一条活动记录。
- 模拟、代操作和租户视图不能创建永久员工或客户受众。普通`Current`调用只执行读取，不会自动创建客户、员工、编号或审计记录。

## 依赖注入与运行时装配边界

- `principal.New(bizctxcap.Service, authz.Service, idccap.BusinessAuditWriter)`声明完整受众/开户服务的显式依赖边界；缺少业务上下文、授权或同事务审计写能力时构造立即失败，不允许开户服务降级为无审计写入。
- `principal.NewReader(bizctxcap.Service)`只暴露无写入的`Current`受众投影，供后台只读列表和审计操作者解析在启动期安全复用。读侧与完整开户写服务分离，避免为了读取受众而制造`principal → audit → principal`对象依赖环；读取器不能兑换开户意图或创建员工受众。
- 任务 2.3 尚未增加运行时注册、路由或控制器，因此当前不存在启动期重复创建。任务 2.5 接入源码插件运行时后，必须从`pluginhost`回调提供的共享 Services 中取得`BizCtx()`和`Authz()`并逐项传入，禁止插件自行`New`宿主服务或创建旁路授权实现。
- `daoPersistence`是`idc-core`内部的无状态持久化实现，由`principal.New`随领域服务创建；它复用生成`DAO`所连接的同一宿主`PostgreSQL`权威后端和调用上下文中的事务，不创建独立数据库连接、缓存或第二套状态源。
- 跨插件复用仍由任务 2.5 的`idccap`调度能力承载；其他插件不得导入`idc-core/backend/internal`或各自重复构造 principal 服务。

## 源码插件授权缺口与安全补偿

`LinaPro`已在`bizctxcap.CurrentContext`声明`Permissions`和`IsSuperAdmin`，但当前源码插件`HTTP`路径的宿主投影只填充身份、租户和数据范围；动态插件路径会完整投影。由于根规则禁止本业务变更修改宿主，任务 2.3 采用以下插件内补偿：

1. 优先识别上下文中实际存在的`IsSuperAdmin`、`PlatformBypass`和任意`idc:admin:*`有效权限。
2. 通过公开`Authz.IsPlatformAdmin`保守排除平台全数据管理员；这只是扩大拒绝范围，不把它声称为精确的超级管理员标记。
3. 显式检查宿主静态权限通配符`*:*:*`。
4. 对`idc-core`维护的完整后台权限目录调用`Authz.BatchHasPermissions`；包含通配符后的查询按宿主上限每批最多 200 项，数量不随业务数据增长。
5. 任一平台管理员或权限查询失败都`fail closed`：员工绑定不执行，客户兑换统一返回不可枚举的开户不可用错误。

仓库级测试以`Go AST`扫描十个 IDC 业务插件的每个`g.Meta`，后台接口必须同时位于`backend/api/admin/`并使用`/admin`路由、恰好声明一个非空`permission`属性；客户或公开接口不得声明后台权限。权限值必须以`idc:admin:*`开头并存在于唯一目录，且后台`API`、`plugin.yaml`菜单/按钮和目录三个权限集合必须完全相等，保证权限既保护真实接口又能由角色稳定分配。测试夹具明确证明漏写权限、目录与路由分类不一致都会失败。当前尚无`IDC`后台接口，因此三个集合均为空；后续新增接口若漏保护、漏登记、不可分配或保留僵尸项，测试会立即失败。

该补偿只依赖宿主公开能力，不查询宿主角色表，也不导入宿主或其他插件的`internal`包。当宿主未来完整投影源码插件上下文时，服务会直接识别快照，授权能力查询仍可作为保守复核。

## 开户兑换事务

`RedeemCustomerOnboarding(currentUserID, intentToken)`先验证当前身份、默认租户、非代操作状态、支持的数据范围和后台受众排除，再裁剪并哈希不透明令牌；明文令牌不会进入持久化接口、数据库字段或审计内容。规范化用户名同样只以`SHA-256`摘要匹配开户意图。

数据库事务按固定顺序执行：

1. 以令牌摘要`FOR UPDATE`锁定开户意图。
2. 校验租户、`verified`状态、已验证联系方式、有效期、宿主注册用户编号、规范化用户名摘要、浏览器和联系方式摘要形状及客户类型。
3. 锁定并确认当前身份不存在任何客户或员工受众，也不存在孤立客户绑定。
4. 以密码学安全随机源分别保留`CUS_`和`BND_`不透明编号；编号保留范围与幂等键只保存摘要。`AUD_`编号只能由审计所有者分配。
5. 插入活动客户受众、客户主体和客户身份绑定，并冻结业务编号的内部拥有者。
6. 以原状态和版本条件把意图从`verified`更新为`consumed`。
7. 通过`idccap.BusinessAuditWriter`同事务提交客户编号、操作、结果、风险和关联编号等业务语义；适配器把输入交给审计所有者，由审计服务从可信上下文解析操作者、执行递归脱敏、分配`AUD_`编号并完成完整性封印。业务领域不再直接写审计表或复制封印算法。

相同令牌和相同用户的重放会锁定同一意图，验证既有活动受众、身份绑定和客户主体后返回原客户编号，并标记结果为复用；不会新增客户、编号或审计。同一用户的两个不同已验证意图并发时只有一个可消费，员工绑定与客户兑换从缺行状态竞争时也只有一种受众可提交；失败事务不会遗留主体、编号、审计或半消费意图。不同身份重放、过期、篡改、身份不一致、后台身份和受众冲突统一安全失败。所有查询与写入次数均为与单个命令相关的固定上限，不按返回行数循环，不存在`N+1`装配。

任务 3.10 在暴露兑换接口前还必须把浏览器随机数原文作为请求证明与现有摘要做恒定语义核验，并实现意图创建、验证码、人机校验、频控和完整端到端门禁。本阶段只消费已经验证的意图，不声称完成这些接口证明。

## 审计与后续边界

- 开户成功必须与审计同事务。复审发现旧实现由`principal`直接插入`business_audit_event`，在通用审计服务后来增加提交时完整性触发器后会产生未封印行并导致整个开户提交失败。现已删除该旁路：中立能力只携带业务语义，`audit.NewBusinessWriterAdapter`是唯一到通用审计写服务的转换边界；审计失败会使开户事务整体回滚。
- 业务编号保留只实现开户事务所需的私有最小能力；其他聚合的通用编号服务和跨插件契约不在本任务中扩张。
- 本阶段没有缓存读写、异步任务、外部网络调用或跨插件运行时调用，不存在缓存一致性与外部副作用影响。

## 国际化

新增并在`zh-CN`与`en-US`保持镜像的稳定错误消息包括：需要认证身份、需要默认商家上下文、需要后台权限、受众冲突、受众状态不一致、身份服务暂时不可用和开户不可用。所有可能到达调用端的授权与持久化失败都包装为稳定`bizerr`，底层 cause 与堆栈保留给服务端诊断；无效令牌、过期、重放冲突、持久化冲突和后台身份不会通过不同错误文案泄露意图或账号存在性。

本阶段没有新增`API`文档元数据或前端可见静态文案，因此没有`apidoc`和页面语言包影响。
