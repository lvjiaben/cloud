## 业务结果

### 退款与红字解耦

- 核心插件只发布已经正式入账且仍然有效的退款事实，合规插件只能读取，不能修改退款或资金账本。
- 红字摄取由源码插件的`pluginhost.Jobs`每分钟在主节点运行，每批最多处理`50`笔；退款完成不等待红字处理。
- 持久游标只在对应退款已经创建任务或确认无需红字后前移。记录失败、进程重启或并发游标变化都不会跳过退款。
- 每笔退款生成自己的确定性任务，同一张原发票的多笔退款按任务创建顺序完成，不能合并成一笔而丢失来源关系。

### 分配、额度与追溯

- 核心退款操作编号使用“来源类型 + 来源编号”的不透明命名空间，避免不同退款来源恰好同号时被合并。合规表支持完整编号长度。
- 只有每个退款明细都能唯一对应一条仍可红冲的原发票分配时才自动分配；一个明细出现多个合格候选时立即转人工，系统不按时间、比例或顺序猜测。
- 人工选择必须完整覆盖本次退款金额，且只能选择任务冻结的合格候选；过期版本、漏选、超额、重复选择或换内容重放都会失败。
- 红字分配不可修改地关联任务、原税务发票、原税务发票分配、原税务发票明细和核心退款分配编号。
- 建立红字分配时同步增加原税务发票分配的退款占用；红冲完成前和完成后都不会把该金额重新变成可开票额度。

### 客户确认与人工完成

- 客户只能读取当前客户自己的安全任务投影，不能看到后台原因、员工身份或私有凭证位置。
- 客户点击“我已完成，重新检查”只调用供应商权威复查；点击和浏览器返回本身都不能推进确认或完成状态。
- 当前生产装配使用`ClosedGateway`，没有创建或调用真实诺诺客户端。外部契约未满足时功能失败关闭，不伪造入口、确认或成功。
- 后台查询和红字处理使用互不替代的精确权限；人工完成必须提交稳定证据编号、`SHA-256`和实际发生时间，可选附带受限私有对象引用。
- 人工凭证、动作历史和业务审计只能追加；没有权威或人工凭证时不能把结果不明任务标记为成功，也不额外要求第二人复核。
- 完成后累计红冲金额小于原发票金额时显示“部分红冲”，等于时显示“已全部红冲”；原发票、归档文件、分配和历史均保留。

## 实现边界

### 跨插件契约与依赖来源

- `idc-core`拥有退款账本和`taxinvoicecap.PostedRefundFeed`、`GetPostedRefund`只读能力。
- `idc-compliance`拥有红字任务、候选、分配、动作、凭证和摄取游标。
- 核心插件启动时创建同一个税务发票来源实例，并把`Source`和`RefundFeed`通过冻结的能力工厂只交给合规插件。
- 合规插件启动时从宿主服务加载一次身份和审计能力、一次管理权限能力和一次核心税务发票运行时，再创建红字服务、摄取器和托管作业。请求路径没有临时创建第二套关键服务图。
- 没有中央业务网关、软件提供方平台操作者、中央结算、中央回调或销售注册依赖；所有状态和游标都在当前安装实例数据库内。

### HTTP 与权限

- 后台读取：`GET /admin/compliance/red-letter-tasks/{taskNo}`，权限`idc:admin:compliance:red-letter:query`。
- 后台明确分配：`POST /admin/compliance/red-letter-tasks/{taskNo}/allocation-resolutions`，权限`idc:admin:compliance:red-letter:handle`。
- 后台凭证完成：`POST /admin/compliance/red-letter-tasks/{taskNo}/manual-completions`，权限`idc:admin:compliance:red-letter:handle`。
- 客户读取：`GET /account/compliance/red-letter-tasks/{taskNo}`，服务层逐次校验当前客户归属。
- 客户权威复查：`PUT /account/compliance/red-letter-tasks/{taskNo}/authoritative-state`，同样逐次校验当前客户归属和任务版本。
- 后台对象不存在与无权访问不泄漏额外数据；客户跨主体编号统一返回不可访问。

### 数据库与性能

- `020-tax-invoice-red-letter.sql`只包含本迭代`DDL`和必需的双语字典种子，没有演示或测试数据，也没有显式写入自增主键。
- 建表、字段、约束、索引、触发器和字典写入都带存在性或冲突保护；迁移原文和重复执行由真实 PostgreSQL 测试覆盖。
- 法律和审计记录不使用软删除。候选、动作和外部证据通过触发器拒绝修改或删除；原发票和文件没有被覆盖或删除。
- 摄取游标以`tenant_id + feed_code`唯一；任务以退款内容摘要稳定防重；动作以任务、动作和幂等摘要唯一。
- 退款来源分页在数据库中一次聚合并限制最多`50`笔；单次退款明细最多`200`项，候选一次集合化读取。详情投影使用固定次数的有界查询，没有随结果行数逐项查库的`N+1`。
- 普通游标读写使用生成的`DAO/DO`。复杂的退款有效额聚合、条件金额推进、不可变历史和乐观并发更新使用单次有界 SQL，并由真实数据库约束与并发测试证明结果。
