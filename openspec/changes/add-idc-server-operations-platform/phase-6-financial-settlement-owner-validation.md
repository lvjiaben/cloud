# 第六阶段财务结清 Owner 接线验证记录

> **`FB-52`部分失效声明：**统一结清 owner 与资金来源证据边界可以保留；为满足旧测试而创建服务器履约单元、资源池绑定和`service_instance`的做法已经失效，只能用于迁移对账。现行结清只发布通用事实，后续消费者按冻结插件契约创建履约意图和可选长期权益。

## 范围与完成边界

本记录覆盖任务`6.12.b`在`idc-core`中的财务 owner 接线：信用购买的非现金账单投影与原子占用、余额/人工收款/合法零金额/百分百优惠的统一结清接线，以及供阶段`7`支付插件调用的最小稳定渠道资金确认能力。

`6.12.b.1`至`6.12.b.3`和渠道支付核心入口`6.12.b.4.1`已经实现。阶段`7`支付插件尚未实现渠道回调、主动查询和对该能力的生产调用，因此`6.12.b.4.2`、父任务`6.12.b`及`6.12`保持未完成，不把核心入口已就绪误报为渠道支付已交付。仓库级国际化门禁仍被禁止在本插件任务中修改的宿主通知预览页 6 个既有缺键阻断。

## 资金与信用事务边界

| 路径 | 提交边界 | 结清失败语义 |
| --- | --- | --- |
| 渠道付款 | `core`锁支付尝试来源和订单账单，在一个本地事务提交商家现金/应收账本交易及渠道支付分配；提交后再请求统一结清 | 真实到账保留，订单不取得履约资格；支付 owner 以相同尝试号、账单、币种、金额和证据摘要安全重试 |
| 客户余额 | 余额借记、商家收入贷记及账单分配先原子提交；随后请求统一结清 | 已扣余额和已分配账单保留，只补做结清，不重复扣款 |
| 经审核人工收款 | 人工收款 owner 先提交正式账本、证明引用、必要的复核和账单分配；随后请求统一结清 | 已确认线下到账不回滚，只阻止履约并重试结清 |
| 信用购买 | 结清协调器从锁定订单推导客户、账单、币种和金额，在同一事务占用额度、创建敞口与流水、写信用账单状态、结清事实和 Outbox | 任一步失败全部回滚，不留下额度占用或半结清事实 |
| 合法零金额/百分百优惠 | 不创建支付交易，结清事实与 Outbox 同事务 | 失败不产生履约资格，精确重放只创建一个结清事实 |

## 版本化支付能力

- `billingcap v1`只接受支付尝试号、订单账单号、三位大写币种、正数最小货币单位金额和小写`SHA-256`证据摘要。客户、订单、商家账户、账单状态、履约状态和资源状态均不允许由支付插件提交。
- 只有精确调用方`idc-payment`可以调用`idc-core`拥有的`billing/channel-payment.confirm`。owner、调用方、服务、版本、方法、空资源引用和空表引用任何一项不匹配都失败关闭。
- `core`重新锁定账单并推导订单、客户和商家账户；同一支付尝试的精确重放复用原交易与分配，改变账单、币种、金额或证据摘要会与不可变资金事实冲突。
- 插件启动装配显式创建并冻结 SPI 工厂、发布 capability descriptor、绑定 invoker 和财务 owner；没有隐藏全局服务定位或跨插件数据库访问。

## 信用账单与客户入口

- 迁移`035-financial-settlement.sql`为订单账单增加独立`credit_amount_minor`和`credit_settled`状态，并以数据库约束保证现金实付、减免和信用金额守恒。信用账单的现金可退额始终为零，普通付款、退款、减免、坏账、合并和拆分拒绝信用结清账单。
- 客户新增`POST /account/billing/invoices/{invoiceNo}/credit-settlements`。请求只包含路径账单号，不接收客户、订单、币种、金额、信用账户或敞口；所有权从当前活动客户主体派生。
- 首次结清后账单进入`credit_settled`，同一客户对同一账单重试仍进入协调器并复用不可变结清；其他已支付或不可访问状态继续失败关闭，跨客户请求不能探测账单存在性。
- 客户与后台账单投影分别增加精确信用结清金额，HTTP 金额继续使用十进制最小货币单位字符串，未暴露数据库主键、信用内部账号、证据摘要或私有资料。

## 数据库、性能与生成边界

- 迁移只有 DDL，没有 Seed 或 Mock 数据；新结清头和来源证据只追加，更新与删除由触发器拒绝。信用敞口、占用流水、账单信用状态、结清事实和事务 Outbox 使用同一显式 PostgreSQL 事务。
- 渠道资金路径使用稳定来源锁和唯一业务来源，账本与支付分配复用既有集合化校验；结清来源最多`1000`条，证据查询最多读取`2001`行用于超限拒绝，不随来源逐行访问外部系统。
- 客户信用入口只执行一次所有权限定账单投影和既有结清协调器调用，没有列表、总数或前端逐行补查。
- API 接口由项目控制器生成流程装配；DAO、DO 和 Entity 由数据库生成流程维护。生成器产生的重复公共 Controller 临时文件已删除，没有保留手工重复声明。

## 审查中发现并修复的问题

1. 客户信用结清首次成功后，入口只允许`pending_payment`，导致同一请求重放被拒绝。现仅额外允许同归属`credit_settled`账单进入协调器，并由不可变结清事实验证回放；真实 PostgreSQL 覆盖首次、重放和跨客户拒绝。
2. 订单取消旧测试把履约单元标记成功并引用不存在的服务，违反现有服务外键。测试现先创建与订单、订单项、履约单元、商品版本、配置和资源池绑定一致的服务，再推进履约单元；没有放宽生产约束。
3. 续费测试 schema 清单漏执行`034`和`035`，运行代码读取新信用金额列时报字段不存在。统一初始化清单现按顺序执行两项迁移，续费真实 PostgreSQL 全包通过。
4. 渠道资金和信用证据校验函数超过项目圈复杂度上限。实现已按事务编排、锁内记账、结清附加及敞口/账户/流水证据拆分，锁序、事务和失败语义保持不变；没有使用 lint 忽略注释。
5. 全包随机顺序暴露异步任务`Create`在纯输入与事务门禁前解析全局数据库，独立运行时会因缺少配置 panic。现先规范化输入并检查调用方事务，再解析默认 DAO；非法输入和无事务各自返回稳定业务错误，20 轮单测、真实 PostgreSQL 异步任务全包及最终完整后端随机回归均通过。

## 影响判断

- API 与数据权限：新增一个从当前客户派生所有权的信用结清动作；渠道资金是无 HTTP 枚举面的精确插件 capability。二者均在目标存在性读取前固定调用身份或客户归属。
- 国际化：新增客户和后台信用金额、信用结清接口的简体中文 API 文档资源；英文继续使用 API 源文本。本插件没有硬编码高风险运行时文案。
- 缓存：无影响。资金、账单、额度、敞口和结清全部读取权威数据库，没有新增缓存事实或失效协议。
- 前端与 E2E：本切片没有新增页面或可观察前端交互；信用购买 UI 和完整信用 E2E 继续由任务`6.14`交付。
- 外部系统：本切片不调用支付宝、微信、易支付或 Provider。渠道验签、主动查询、回调持久化和实际 capability 调用由阶段`7`支付插件完成。
