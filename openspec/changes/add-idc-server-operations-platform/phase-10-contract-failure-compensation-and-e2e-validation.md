# 第十阶段合同失败补偿与 E2E 收口验证记录

## 本轮结论

本轮完成了每套安装本地运行的必签合同失败处理基线：供应商权威确认合同拒签、过期、撤销或终态失败后，系统冻结当时的处理策略和截止时间；处理期内只允许有权后台人员明确重新发起或立即取消，截止时间到达后由托管作业处理，不会自动重复发起收费合同。

安全自动处理仅适用于已经付款、仍停在合同门禁前、库存尚未消耗且资源开通尚未开始的订单。符合条件时，`idc-core`一次事务停止待执行交付、释放库存、取消待开通服务和业务操作，并创建唯一退款交接与`billing.refund.requested`事件。核心插件的主节点托管作业随后把交接转换成现有统一退款单和同一套资金来源执行命令；只有统一退款真实成功后才把交接、补偿和订单改成完成或已退款。处理中页面和接口只显示“退款处理中”，绝不把退款申请冒充为钱已经退回。任何已开始履约、金额不一致、资金来源异常、图关系异常或处理结果不明确的情况都保留原事实并进入人工核对。

## 文件与边界

- 跨插件命令由`idc-core/backend/cap/contractcap`拥有，合规插件只提交冻结后的合同终态、订单号、策略版本和截止时间，不访问核心插件内部模型。
- 核心补偿实现位于`idc-core/backend/internal/service/contractcompensation/`，迁移为`044-contract-failure-compensation.sql`。
- 统一退款接线位于`idc-core/backend/internal/service/billing/billing_contract_refund_worker.go`，由`idc-core-contract-refunds`主节点托管作业有界执行；它不直接调用支付渠道，不创建第二套资金事实。
- 未成熟佣金底座位于`idc-core/backend/internal/service/commission/`，迁移为`061-commission-refund-reversal.sql`，由`idc-core-commission-refund-reversal`主节点托管作业消费统一退款成功事件；只冲回仍处于待成熟状态的金额，已成熟金额保持不动。
- 合规处理策略、失败案件、托管作业和立即取消实现位于`idc-compliance/backend/internal/service/contractfailure/`，迁移为`025-contract-failure-compensation.sql`。
- 后台策略和立即取消入口位于`idc-compliance/frontend/`，通过插件页面机制加载；没有向`apps/lina-vben/apps/web-antd/`写入 IDC 页面、组件、接口、路由、状态、多语言或依赖。
- 本轮没有改动`web-customer`。原因仅限当前补偿入口属于后台处理动作；第十阶段已有客户合同、签署和开票页面仍保留在`web-customer`，没有被推迟或迁回旧 Portal。
- 本地合规网关继续只依赖当前安装的数据库、购买方供应商账号和本地密钥，不存在软件提供方中央业务网关、中央结算、中央回调或平台操作者依赖。

## 审查中修正的问题

1. 把业务操作状态和事件由逐条数据库写入改为一次集合更新与一次批量事件写入，数据库请求次数不再随业务操作数量线性增长；订单图仍硬限制最多一千行并在超限时失败关闭。
2. 管理员立即取消的执行失败路径不再丢弃队列恢复错误；恢复失败会带上下文返回，避免案件长期卡在处理中却没有可见原因。
3. 策略创建时间从错误的 Unix 秒修正为项目统一的 Unix 毫秒，并补齐接口字段说明。
4. 加强`TC004`断言：必须等待确认框关闭并看到操作后的准确提示，不能再误把确认框说明当作成功结果。
5. 修正合同管理页左侧裁切和合同编号挤压，增加操作后截图并完成人工图片审查；页面没有原始翻译键、重叠或把退款申请显示成退款完成。
6. 增加已开始履约时必须转人工核对的安全门禁测试，并保留结果不明最多五次后转人工核对的真实 PostgreSQL 测试。
7. 补齐此前被`12.5`阻断的未成熟佣金冲回：佣金快照锁定订单、账单项、计算基数、原账单项金额、规则版本、币种和受益人；退款按账单项累计退款比例计算目标冲回额，只减少待成熟部分，追加唯一冲回记录和消费回执。同一退款重放不会重复冲回，已经成熟的佣金不会被后台静默扣回。
8. 合同补偿不再仅凭资金退款成功就标记全部完成；它还会等待佣金冲回事件真正发布。佣金事件进入死信或结果不明时，整个补偿转人工处理，保留资金、订单和佣金事实供核对。

本轮`lina-review`没有遗留严重问题。缓存无影响：新增服务不持有运行时缓存；数据权限由合规插件既有管理授权器按精确权限和目标合同号执行；运行依赖由核心插件启动装配创建，再通过`contractcap`公开契约传给合规插件的路由服务和托管作业，均使用同一安装数据库且没有请求内临时创建服务图。
