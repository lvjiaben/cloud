# 阶段 6.5.b—6.5.d 服务续费执行验证

> **`FB-52`失效声明：**旧`renewalresourcecap/v1`按服务器渠道、资源池和 Provider 推断续费拥有方的模型已经失效，不能作为当前续费执行完成证据。现行续费按长期权益冻结的业务拥有方 ID 和契约版本精确路由：外部确认模式走持久任务，本地权益模式只在契约明确声明时推进，未知能力失败关闭；一次性交付没有入口。下文仅用于迁移对账和删除旧接缝，不得恢复兼容层。

## 交付边界

- `idc-core`已实现从当前服务配置和当前有效续费价生成不可变续费报价，确认后创建独立续费账单，并支持客户手动余额付款与托管自动续费。
- `core`与`idc-resource`之间使用版本化`renewalresourcecap/v1`契约。`core`只保存不透明能力与任务引用；资源能力、Provider 任务和证据仍由 resource owner 独占。
- `idc-resource`只在启用渠道、启用资源池、活动资源映射和最新完整 27 项能力快照同时成立时返回短期证据。明确支持续期才创建 Provider 任务；续期与资源到期日均明确不受管理时才返回`local_entitlement`。
- 本切片没有新增 HTTP、管理页面或 Portal 页面；客户账单与自动续费页面由`6.7`实现，浏览器整链路由`6.9`验证。

## 关键不变量

- 续费报价冻结服务、商品版本、配置、明确币种、周期、税务、价格构成、原到期日、预计新到期日、资源路由和能力证据。后续改价不覆盖旧报价，新报价使用新的当前有效续费价。
- 余额付款只能消费账单的同客户、同币种余额，金额、客户、币种和账单均从权威记录派生；余额不足不创建虚假结算，只保留待付款账单和可重试事实。
- 自动续费使用策略版本、服务当前到期日和幂等摘要复用同一报价、账单、业务操作与支付来源。重放不能重复扣款、重复创建 Provider 任务或重复推进到期日。
- `provider_confirmed`只有在 resource owner 返回与冻结请求精确关联的任务成功证据后才推进到期日。失败保持原到期日；结果未知、任务冲突、能力过期或路由事实变化进入人工处理并保持原到期日。
- `local_entitlement`不创建虚假 Provider 任务或上游到期快照，只在资金结算成功后推进 core 本地权益。能力未知、条件式、快照不完整或过期不能静默降级成本地续费。
- 客户入口只从当前活动客户主体派生所有权；托管 worker 使用独立可信构造，不伪造客户主体。同步报价和余额结算只访问本地 PostgreSQL，不调用 Provider。

## 生产调度与性能边界

- 主节点每 30 秒执行一次自动续费和 Provider 续费协调任务，生产批量固定为 32，服务层硬上限为 64；从节点不重复调度。
- 到期候选、重试候选和 Provider 操作均使用有界集合查询与稳定排序；服务、策略、价格和最近尝试由集合查询或单事务锁定装配，不在同步客户请求中逐项调用 Provider。
- resource owner 的 Provider 执行器按渠道在批次内复用 Provider 会话并保证清理；能力读取和任务状态读取只返回有界脱敏投影，不返回凭据、上游资源号或原始响应。
- 全量测试第一次使用 Go 默认包并行度时，隔离 schema 的并发 DDL 使本地 PostgreSQL 报告共享锁内存耗尽；改用`-p 1`串行包隔离后全部通过。该现象没有业务断言失败，也不改变生产查询路径。

## 复审结论

- 按`lina-review`复核能力证据、客户所有权、同币种结算、事务边界、任务关联、状态推进、幂等、批量上限、索引和多语言后，未发现本切片新增的 P0/P1 问题。
- 后续生命周期全量回归发现并修复自动续费尝试的 PostgreSQL 锁等待快照问题：owner 行锁与最新尝试读取已经拆成两个语句，确保等待锁后的新快照能看到前一事务刚提交的尝试。同一服务并发自动续费真实 PostgreSQL 测试连续 20 轮只保留一个尝试事实，不再因重复序号返回唯一键冲突；对应追踪项为`FB-5`。
- 数据权限：没有新增列表、导出或管理写接口。客户报价、确认和支付使用当前客户主体；调度入口只由插件生产任务构造，不形成 HTTP 绕过路径。
- 缓存：无影响。服务权益、价格、账单、尝试、能力快照和任务均以 PostgreSQL 为权威源，没有新增缓存或陈旧窗口。
- API、前端与 E2E：本切片无变更，不提前宣称`6.7`和`6.9`完成。
