# 第二阶段 Outbox 与异步任务验证记录

## 范围与职责

本记录覆盖任务 2.4 的事务`Outbox`与异步任务基础服务。两个服务均属于`idc-core`内部运行内核，当前不暴露`HTTP API`、管理页面或跨插件公开能力，也不自行启动后台线程；任务 2.11 将通过宿主`pluginhost.Jobs`注册轮询作业。

- `outbox`负责与权威业务写入同事务追加事件，以及提交后的至少一次领取、续租、发布、退避、死信和结果未知收敛。
- `asynctask`负责外部业务写操作的持久任务、每次尝试证据、租约、明确失败重试、结果未知冻结和人工接管。
- `Outbox`不是外部业务任务表，不存放人工处理人或人工原因；人工接管只发生在`async_task`。

## 事务与幂等边界

`Outbox.Enqueue`和异步任务创建只接受已经开启数据库事务的上下文。调用方拥有提交或回滚权，服务不会另开事务，因此订单、账单、服务或其他权威状态与对应事件、任务只能同时提交或同时回滚。

事件和任务均只持久化幂等键的`SHA-256`摘要，不保存或回显原始键。相同幂等范围和相同规范化输入收敛到既有记录；相同键但不同版本化信封会返回稳定冲突，禁止悄悄复用错误任务。调用方必须先把载荷、元数据、请求、响应和自由文本诊断转换为有大小上限的最小脱敏证据；服务对结构化键的常见秘密后缀以及自由文本中的常见凭据赋值、授权头、Bearer 和私钥标记再做防御性拒绝。该扫描不能替代领域专用投影和任务 2.7 的统一秘密/日志治理，禁止把原始第三方响应、访问令牌或未处理的个人敏感信息传入运行表。

## 状态与恢复语义

| 对象 | 原状态 | 条件 | 目标状态 | 自动重试 |
| --- | --- | --- | --- | --- |
| `Outbox` | `pending/retry_wait` | 到达可用时间并成功领取 | `processing` | 是 |
| `Outbox` | `processing` | 明确发布成功 | `published` | 否 |
| `Outbox` | `processing` | 明确未产生效果且可重试 | `retry_wait` | 有界 |
| `Outbox` | `processing` | 明确失败且次数耗尽 | `dead_letter` | 否 |
| `Outbox` | `processing` | 发布结果无法确定 | `result_unknown` | 否 |
| `Outbox` | `processing` | 租约过期且仍有次数 | 再次`processing` | 是，消费者必须幂等 |
| `Outbox` | `processing` | 最后一次租约过期 | `result_unknown` | 否 |
| 异步任务 | `pending/retry_wait` | 到达可用时间并成功领取 | `running` | 是 |
| 异步任务 | `running` | 有明确成功证据 | `succeeded` | 否 |
| 异步任务 | `running` | 明确未产生外部效果且可重试 | `retry_wait` | 有界 |
| 异步任务 | `running` | 明确永久失败 | `failed` | 否 |
| 异步任务 | `running` | 明确失败且次数耗尽 | `dead_letter` | 否 |
| 异步任务 | `running` | 超时、断线、进程退出或租约过期 | `result_unknown` | 否，必须先查询外部结果 |
| 异步任务 | `failed/dead_letter/result_unknown` | 受信任的后台流程接管 | `manual_takeover` | 否 |

通用人工接管只负责停止自动执行、固定处理人和脱敏原因，不提供通用“强制成功”、直接重试或终止接口。支付、退款、资源等具体领域后续必须依据外部查询和业务证据决定下一步。

## 并发领取与租约隔离

领取在短事务中按默认商家`tenant_id = 0`、状态、可用时间和稳定顺序读取有限批次，并使用`FOR UPDATE SKIP LOCKED`隔离并发 Worker。领取会递增尝试号，写入不可预测的租约令牌和到期时间；异步任务在同一事务批量追加对应`attempt`证据，禁止逐行事务或随结果行数增长的`N+1`查询。构造服务时还会同时校验批次数与单条最大证据的乘积，确保 Outbox 单批载荷与元数据不超过 64 MiB；异步任务把读取/返回的载荷与结果快照、以及写入 attempt 的请求副本合并计算，单批序列化证据不超过 32 MiB。不能用多个合法单项上限组合出数 GiB 请求。

续租、成功、失败和结果未知转换必须同时匹配默认商家、业务编号、运行状态、租约令牌和尝试号。旧 Worker、过期租约、重复完成或错误任务编号统一按租约丢失处理，不能覆盖新的领取结果，也不通过差异化错误泄露记录是否存在。

生成`DO`无法用`nil`表达数据库`NULL`。终态和释放租约的转换先使用生成`DO`及完整 fencing 条件完成状态比较交换，再在同一事务内仅对已确认记录使用固定列名把`lease_expires_at`清为`NULL`。这是避免租约部分索引永久膨胀的受控窄例外，不允许使用动态`map`或零时间代替`NULL`。

## 退避与性能边界

明确可重试失败使用有上限的指数退避和确定性抖动，避免大量任务同时恢复造成惊群；达到最大尝试次数后进入死信。批量领取、过期恢复和尝试插入均有固定批次上限，查询使用任务 2.1 已建立的状态、可用时间和租约部分索引。服务不在循环中逐行查询或开启事务。

## 数据权限与审计边界

本阶段的服务是未接入路由的插件内部系统能力，只允许受信任的领域服务和后续宿主作业调用，并固定访问单商家默认租户。人工接管方法虽然记录宿主员工编号、时间和脱敏原因，但本阶段不直接依赖宿主员工目录；可信调用者必须先证明处理人是当前管理数据范围内可见的有效员工。任何后续`HTTP`入口必须先完成`idc:admin:*`权限、目标对象和处理人员数据可见性、最近重新认证和业务审计，再调用该方法。禁止直接把内部服务注册为无保护接口。

客户归属通过异步任务中创建时已验证并冻结的`customer_no`投影支持数据库阶段过滤。当前没有列表、详情、导出或面向客户的候选接口，因此没有新增可观察的数据权限路径。

## 国际化、缓存与接口影响

所有可能到达调用端的参数、事务、幂等冲突、租约丢失、状态冲突和暂时不可用错误均使用稳定`bizerr`代码，并在`zh-CN`与`en-US`提供镜像消息。运行载荷中的错误摘要属于已脱敏诊断证据，不作为翻译源文本。

本任务没有缓存读写，不改变缓存一致性边界；没有新增`HTTP API`、OpenAPI 契约、前端路由、组件或用户可观察页面，因此不触发浏览器`E2E`。本任务没有新增或修改`SQL`，复用任务 2.1 的表、约束和索引。
