# 第十阶段本地数据生命周期执行与恢复验证记录

## 1. 结论与边界

本记录证明任务`10.7.d.2`已经在每套安装自带的本地合规网关内完成供应商授权撤销、受控证据导出、法律保全、分类型留存删除和恢复核验执行闭环。实现不连接软件提供方业务服务，不创建中央网关、中央结算、中央回调、平台操作者或跨客户数据路径，也没有实现或启用真实腾讯、诺诺客户端。

本记录形成时腾讯`10.4.b`和诺诺`10.4.c`均受外部证据阻断。`2026-08-14`后腾讯改为官方公开契约与购买方运行时能力门禁，诺诺仍受购买方自有账号、接口权限、数据处理协议和正式契约证据阻断。这些供应商边界不影响本地生命周期服务、关闭状态和恢复演练，但真实供应商侧撤权仍必须由当前商家在自己的供应商控制台执行，禁止伪造完成证据。

本任务没有新增页面、公开 HTTP API 或用户交互，没有进入第 15 阶段，没有修改或删除`web-customer`和旧 Portal。`10.7.d`父任务仍需按`tasks.md`独立判断，不因本子任务完成而连带勾选`10.7`、`FB-11`或任何第 15 阶段任务。

## 2. 根因复核

任务`10.7.d.1`只建立了生命周期策略、法律保全事件、导出事件、供应商授权事件和恢复验证记录表，以及双语责任与备份恢复说明。既有单主体撤销服务只把主体状态改为`revoked`，供应商写入门禁和用量采集不会读取授权停止状态；数据库也没有留存处置记录、受控删除入口、加密导出执行或逐条恢复完整性核验。因此旧表、旧说明和旧 Portal 验证只能作为底座，不能证明`10.7.d.2`完成。

迁移`012-local-data-lifecycle.sql`还把`action_code`定义为 16 字符，却允许长度为 18 的`processing_stopped`，导致该必需事件实际无法写入。新增升级迁移在不修改历史迁移的前提下修正列宽，并补齐本地执行状态、幂等摘要和不可变处置记录。独立审查还发现，若只增加单向停止状态，商家完成独立重新授权后会被永久锁死；因此同一升级迁移和本地服务同时补齐了受审的`processing_resumed`恢复转换。

## 3. 冻结的执行规则

| 功能细节 | 冻结结果 |
|---|---|
| 供应商撤权 | 继续复用既有管理端精确权限、最近五分钟完整登录和本机签名路径；本地网关先把供应商处理状态改为`stopped`，再以固定原因`supplier_authorization_revoked`撤销不透明主体 |
| 停止新处理 | 供应商写入门禁与只读采集领取都读取 PostgreSQL 中的供应商处理状态；停止后不再发出新供应商调用，在途和结果未知操作仍保留证据并走查询或人工接管 |
| 撤权重试 | 同一稳定幂等键可以补完中途停止的“停新—主体撤销—事件完成”步骤；重复执行不追加第二组`processing_stopped/revoked`事件 |
| 独立重新开通 | 重新授权仍是另一项需要近期完整登录的操作；先创建新的不透明主体，再追加`processing_resumed`并恢复本地处理状态，重试不会创建第二个主体或第二条恢复事件；只有当前安装确实装配了已审查采集器时才恢复采集调度 |
| 历史与密钥 | 主体、查重摘要、身份操作和法定证据继续保留；撤销主体、实例、供应商授权或服务二进制都不会隐式删除密文或销毁密钥 |
| 凭据边界 | 供应商主体撤销与本地凭据生命周期保持两个独立受权操作；撤权请求不顺带撤销`secretcap`句柄，双语说明不再虚报不存在的凭据撤销执行 |
| 证据导出 | 单次最多 16 条，只接受固定供应商、精确路由和/或精确证据号；调用方临时提供 256 位导出密钥，服务生成`AES-256-GCM`加密包后清零密钥，只保存范围摘要、包摘要、员工、状态和过期时间 |
| 法律保全 | 放置和解除只追加不可变事件，不修改原证据；任何活动保全都使对应分类的留存执行失败关闭。聚合记录映射尚未交付时，带聚合 HMAC 的保全保守阻断整个分类，避免误删 |
| 留存删除 | 每次最多 1,000 行；短期进程 nonce 与分别批准的用量、费用和`SLA`投影可删除，并留下不可变选中集合摘要。供应商回调、供应商证据和审计始终拒绝物理删除 |
| 密码学擦除 | `crypto_erase`策略只记录“需要独立受审终态动作”，当前执行器不销毁被多个历史密文引用的共享密钥 |
| 恢复写阻断 | 恢复核验前必须把腾讯、诺诺两个处理状态都持久化为`stopped`；仅由调用方声称“已阻断”而数据库仍允许写入时，核验直接拒绝 |
| 恢复核验 | 完整比对 18 个内嵌迁移及校验值、检查七类策略和三个用途隔离密钥环，集合读取主体与查重摘要并逐条解密主体和回调证据，结果追加到`idc_gateway_restore_verification` |

## 4. 数据库、服务和调用接线

- `018-local-data-lifecycle-runtime.sql`新增两个固定供应商的本地处理状态、授权事件操作摘要、不可变留存处置记录、法定分类策略约束和受服务控制的运营投影删除门禁；迁移只含幂等 DDL 与两个固定本地运行状态的系统引导 DML，不含客户、订单、金额、供应商凭据、Mock 或中央身份数据。
- `internal/datalifecycle`是本地进程内服务，使用启动期共享的数据库池、安装标识、供应商主体密钥环和回调证据密钥环；不使用全局服务定位、逐请求构造、缓存、远程开关或软件提供方网络依赖。
- 既有供应商撤销与重新开通管理服务从已授权宿主会话生成`staff:<user-id>`员工编号和稳定证据摘要，通过既有 loopback 签名请求交给本地网关。公开管理 API 的路径、方法、请求 DTO、响应 DTO和权限标识没有变化。
- 写入门禁在取得业务写入资格前同时锁定本地实例和精确供应商处理状态；用量采集启动和租约领取同样要求状态为`allowed`。状态为`stopped`时两条路径均失败关闭。
- 留存执行使用固定表白名单和集合化查询，不接受任意表名或 SQL。受控删除需要事务内本地执行标志；普通更新、删除和服务终止仍被数据库触发器拒绝。法定证据没有删除分支。
- 恢复核验对迁移账本执行一次集合读取，对主体和查重摘要执行两次集合读取，对回调证据执行一次流式读取；不会按每条记录再次查询数据库，也不会调用真实供应商。

## 6. 审查与影响记录

- `lina-feedback`：根因确认是`10.7.d.1`只有记录模型，没有运行执行链；本次直接纳入现有活跃变更的`10.7.d.2`，没有新建重复变更或把历史 Portal 证据当作完成证明。
- `lina-review`：发现并修正三项完成阻断——数据库影响行数异常时可能误返回成功、撤权说明错误声称同一步撤销本地凭据，以及单向停止状态会让独立重新授权永久无法恢复；修正后重新执行真实 PostgreSQL、两侧全模块、静态检查、发布构建和严格规范门禁。
- 架构：所有新能力闭环在`idc-compliance/central-gateway`及既有插件到本机网关接线内，没有修改`lina-core`、宿主领域契约或其他插件；独立安装仍只访问本地数据库与商家自己的供应商。
- 数据权限：没有新增公开列表、详情、下载或写入 API。管理端撤销继续先执行宿主精确权限与最近登录校验；生命周期服务是当前安装内、受信的内部执行服务，不引入跨租户、跨安装或对象存在性暴露。
- 接口：公开 API 契约无变化；既有本机签名撤销载荷只增加服务端生成的供应商代码、员工编号和证据摘要，仍为单次本机调用，不增加前端调用次数或瀑布查询。
- 性能：导出固定最多 16 条、留存固定最多 1,000 行；恢复是离线完整性任务，使用集合读取和逐行流式解密，不存在随返回行再发起数据库查询的`N+1`路径。
- 数据库：法律、授权、导出、留存处置和恢复记录不使用软删除；迁移幂等、对象名不超过 PostgreSQL 63 字节，升级测试在真实 PostgreSQL 连续执行并核对校验账本。系统引导 DML只创建腾讯、诺诺两个不含业务数据的本地处理状态。
- `i18n`：没有新增运行时用户可见文案、菜单、按钮、错误翻译或 API 文档源文本；中英文`DATA-LIFECYCLE`说明同步更新。
- 缓存：没有新增或修改缓存，不存在缓存一致性影响。
- 前端与 E2E：没有修改页面、路由或浏览器交互，本任务不触发前端构建和 Playwright 用例；第`10.19`的完整客户旅程 E2E 仍按阶段顺序保持未完成。
