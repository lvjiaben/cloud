## 领域和能力边界

| 能力 | 已交付边界 | 明确未交付边界 |
| --- | --- | --- |
| 法定资料变更 | 只记录变更字段类别、原因、来源认证状态、来源版本和不透明认证案件号；同一客户仅一个活动申请 | 原始姓名、证件号、统一社会信用代码、证件、执照、人脸与上传材料继续由合规领域拥有；合规审核决议尚未装配 |
| 账户状态 | 独立`AccountLifecycleService`、固定状态矩阵、乐观版本、追加式状态历史和同事务审计；生产`AccountStateAuthorizer`使用宿主`Authz`校验精确权限并保守解释数据范围；通用入口禁止`anonymized` | 后台状态 API、权限目录和启动装配尚未实现；部门/本人数据范围没有客户归属投影时明确拒绝 |
| 注销预检 | 客户领域定义版本化批量契约，只接收稳定检查代码和聚合数量；缺失、重复、过期、未知或依赖错误均失败关闭 | 账本、服务、账单、合同和业务操作领域的真实聚合器尚未装配 |
| 注销申请 | 有硬阻碍只返回检查结果，不生成同意或注销授权；无硬阻碍时同事务追加`account_closure`同意并创建待复核申请 | 批准、身份撤销、最终重检和策略化匿名化尚未实现，旧检查快照不能直接触发注销 |
| 数据导出 | 最近重新认证证明绑定完整导出意图并在事务外单次消费；事务内追加`data_export`同意、创建真实异步任务、请求关联和审计 | worker、私有对象生成、短期下载地址、下载重新鉴权和状态展示尚未实现 |

客户自助入口统一先执行直接客户身份门禁，再比较输入`customer_no`与当前绑定，之后才允许格式校验、重新认证、跨域检查或数据库访问。超级管理员、平台绕过、后台权限、协助、模拟、租户代入和`ActingUserID`上下文在任何依赖调用前拒绝。

后台账户状态能力没有混入客户自助`Service`。它先拒绝委托上下文并只读确认已经存在的直接活动员工受众，再调用强制注入的精确授权器检查状态修改权限和目标客户数据范围；任意其他`idc:admin:*`权限不能替代该授权结果。状态写路径禁止调用`EnsureCurrentStaff`，最终被拒绝的请求不能先创建或重绑永久员工受众；首次员工绑定必须由未来独立后台受众装配流程完成。源码插件上下文可能不携带`Permissions/IsSuperAdmin`快照，状态服务不再根据空快照提前拒绝；`PlatformBypass`本身也不授予状态权限，最终仍须精确权限、宿主通配权限或平台管理员权威证据。

当前状态授权器只允许宿主全量和商家数据范围，因为客户表尚无可将部门或本人范围转换为目标客户 SQL 条件的稳定归属投影。部门、本人、零值、不支持数据范围、模拟、代操作、租户代入、错误目标编号和宿主授权失败均在状态持久化之前返回统一不可访问结果。

`AccountStateAuthorizer`新增的运行期依赖均为宿主拥有的公开能力：`bizctxcap.Service`提供当前请求快照，`authz.Service`提供权限和平台管理员权威查询。两项依赖由未来`idc-core`路由注册回调从`registrar.Services()`取得并在启动期构造一次授权器，再显式传入`NewAccountLifecycleService`；当前没有路由和启动组合，因此不伪造已装配状态。授权器不持有缓存、权限快照或本地派生状态，不产生集群共享实例问题。

## 数据最小化、留存和匿名化

- `customer_legal_change_request`不包含拟替换法定值或材料字段，申请事务也不更新个人/企业认证投影。审计只保存类别、稳定代码、版本和不透明案件号。
- `customer_account_state_history`是追加式生命周期证据，数据库`CHECK`固化允许的运营状态矩阵；只有未来注销专用来源可进入`anonymized`，不存在从匿名化状态恢复的路径。
- `customer_closure_request`只保存版本化预检的六类聚合数量、保留策略、匿名化策略和同意编号。资金、服务、账单、合同或进行中操作存在时不落申请；`legal_retention`不是硬阻碍，它表示完成注销后仍必须保存的法定证据。
- 注销普通资料的匿名化不能删除账本、支付退款、合同、发票、实名决定、审计、迁移映射或其他法定留存证据。工作流表因此没有软删除或普通物理删除语义。
- `customer_data_export_request`不复制异步任务执行状态；唯一执行状态继续由`async_task`持有。请求表只保存不透明请求、同意、任务关联、导出范围/格式、主体版本和证明签发时间。
- 原始重新认证证明、会话编号、客户资料和最终文件不进入导出请求或任务载荷。任务载荷只含 schema 版本、导出范围、格式和客户主体版本。

## 事务、幂等与并发

- 四类公开编号通过`business_number`在业务事务内以加密随机数生成并按客户与幂等范围收敛；DAO、DO 和 Entity 由插件级生成命令产生，没有手改生成文件。
- 法定资料申请、账户状态迁移、注销申请和导出请求均先锁定客户主体，再重验状态与版本。相同幂等键改变语义返回稳定冲突，完全相同重放返回原结果。
- 数据导出按“事务外消费最近认证证明 → 客户事务内锁定主体 → 追加同意 → `asynctask.Service.Create` → 写请求关联 → 写审计”的顺序执行。审计失败时，同意、任务、请求和业务编号一起回滚；已经消费的证明不会因数据库回滚恢复可重放。
- 已提交导出命令的完全相同幂等重放只返回不敏感的请求号和任务号，不再次消费证明或创建任务。该行为不授予文件访问，下载仍必须独立校验所有权、有效期和访问策略。
- 注销预检是请求时快照，不是完成授权。最终完成路径必须重新调用同一批量契约，从而防止检查后新增服务、欠款或合同的竞态。
