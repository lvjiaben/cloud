# 第十阶段合同签署经办人、独立提交与统一短信验证记录

## 结论

任务`10.8.d.2`已经完成本地实现与定向验证：企业合同签署经办人使用独立目录，客户可以在`@lina/web-customer`新增、完成本人实名认证、验证手机号和停用；后台只能取得当前企业中全部验证通过且仍有效的安全候选。普通通知联系人不会自动成为签署经办人，停用也不会改写已经冻结的合同。

合同预览继续是独立动作，不会在生成预览时调用腾讯。预览冻结个人实名认证本人及已验证手机号，或后台明确选择的企业经办人姓名、手机号、客户归属、实名版本、手机号验证版本和授权版本。管理员检查不可修改预览后，必须再通过精确权限`idc:admin:compliance:contract:create`执行“提交签署”；本地合规网关才使用腾讯官方 SDK、已经确认的模板填写位置和签署人对应创建流程。数据库只保存本地不透明流程路由，不把腾讯外部流程号暴露给普通业务插件。

整个平台的短信继续只由`idc-notify`配置和发送。合规插件仅调用通知插件公开的版本化验证码能力，不拥有短信账号、服务商、签名或模板配置，也不直接调用阿里云、腾讯云或短信宝。当前短信服务商、用途模板、变量对应或发送结果不安全时全部失败关闭，不自动换通道、不自动重发，也不伪造成功。

本项没有修改`apps/lina-vben/apps/web-antd/`。IDC 后台页面仍由对应插件`frontend/`拥有，登录后的签署经办人客户页面位于`apps/lina-vben/apps/web-customer/`，公开官网无影响。

## 问题原因与本轮审查修复

统一短信方向复核发现，若每个业务插件各自保存一套短信账号和模板，管理员切换服务商后会出现配置分裂、旧模板误用和无法统一判断发送结果的问题。因此短信服务商选择、凭据、签名、模板对应和实际投递统一收口到`idc-notify`；业务插件只保留自己的验证码用途和验证事实。

完成实现后的审查还发现，合同流程最终状态原先先提交数据库、再追加业务审计。审计不可用时会留下没有对应审计记录的合同状态，与`BusinessAuditWriter`要求的“业务变化和审计一起成功或一起失败”不符。本轮已经修复：

- 创建本地`submitting`流程与“开始提交”审计在同一 PostgreSQL 事务中提交；审计失败时不会调用腾讯。
- 把`signing`、`result_unknown`或`failed`最终状态与对应审计放进同一 PostgreSQL 事务；审计失败时最终状态整体回滚。
- 真实 PostgreSQL 用例已经证明：腾讯调用之后若最终审计失败，合同仍保持`pending_launch`，本地流程保持`submitting`，供应商路由不会被错误提交，后续也不会因为普通页面重试而危险重发。

客户页面审查同时修复了一个可见问题：短信发送结果不明确时，全局请求层曾先显示后端英文`result unknown`，随后页面才显示双语安全提示。现在只有该请求关闭全局原始错误提示，由页面显示“发送结果暂时无法确认，请勿重复点击；稍后主动获取新的验证码”对应的中英文文案；真实浏览器断言原始英文不再出现。

## 主要实现边界

| 能力 | 所有者与实现结果 |
|---|---|
| 企业签署经办人目录 | `idc-compliance`迁移`012-contract-signer-directory.sql`和`contractsigner`服务；目录与通知联系人分离，原始姓名、证件和手机号使用本地秘密能力保护，列表只返回脱敏结果 |
| 客户操作 | `@lina/web-customer`的合同签署经办人页面、API 客户端、路由和双语资源；沿用`web-antd`同结构的 Vben/Vite 写法，不写入宿主 |
| 本人实名认证 | 合规插件按经办人和当前企业归属创建、主动查询并冻结验证版本；浏览器返回不能直接证明成功 |
| 手机号验证 | 合规插件调用`idc-notify/backend/cap/securitycodecap`；通知插件负责当前短信通道、验证码、频控、模板和发送结果，合规插件只保存经办人的手机号验证事实 |
| 后台候选 | 合规插件插件后台接口只返回当前企业、实名通过、手机号通过、授权有效且未停用的脱敏候选，并要求合同创建精确权限 |
| 不可修改预览 | `electroniccontractpreparation`在本地加密快照中冻结订单、服务、金额、模板语言、签署顺序和签署方版本；生成预览不会调用腾讯 |
| 独立提交 | 单独的提交接口、幂等摘要、本地流程号、结果未知保护和事务审计；同一请求只允许一次越过供应商写边界 |
| 本地合规网关 | 每套安装自带的`idc-compliance/central-gateway`独立进程；使用腾讯官方 SDK 创建模板流程，仅向插件返回`lwr_...`本地路由 |
| 统一短信服务商 | `idc-notify`在同一入口选择阿里云、腾讯云或短信宝；任一时刻只有一个验证通过的当前短信服务商，不匹配的旧服务商模板不能发送 |

## 服务商契约依据

- 阿里云短信发送使用官方`SendSms`契约，模板由`TemplateCode`选择，签名由`SignName`选择，变量通过`TemplateParam`传入：[阿里云 SendSms](https://help.aliyun.com/zh/sms/developer-reference/api-dysmsapi-2017-05-25-sendsms)。
- 腾讯云短信使用官方`SendSms`契约，按`SmsSdkAppId`、`SignName`、`TemplateId`和模板参数发送：[腾讯云 SendSms](https://cloud.tencent.com/document/api/382/38778)。
- 短信宝官方发送接口以完整短信内容`c`提交，并可选传产品编号`p`，没有阿里云或腾讯云同形态的发送时模板 ID；因此后台不会为短信宝伪造模板 ID 字段：[短信宝发送接口](https://smsbao.com/openapi/213.html)。

以上只决定适配器参数，不改变业务规则。每套安装实例使用自己配置的服务商账号并直接与服务商结算，软件提供方不转发短信、不代持购买方凭据，也不提供中央短信业务网关。

## 没有冒充通过的门禁

- 启用全部真实 PostgreSQL 用例执行合规插件`go test ./...`时，`electroniccontracttemplate`的既有`TestElectronicContractTemplatePostgreSQLConcurrentEnableKeepsOneVersion`在保存供应商对应时稳定报告“合同模板当前状态冲突”。该用例属于仍未勾选的`10.8.c.4`，不在本项签署经办人、统一短信或独立提交改动中。本记录保留该失败，不把“合规插件全部真实 PostgreSQL 用例”写成通过；`10.8.c.4`仍保持未勾选。
- 根 E2E 治理检查仍报告`11`项本项之外的既有问题：八个插件的`scaffold.json`不是 TypeScript E2E、根`TC019`源码插件归属问题、根`TC004`高风险插件生命周期用例未串行、根`TC009`系统配置用例未串行。本项新增的`TC003`符合模块本地编号与串行隔离要求并已通过；未修改公共`hack/tests`绕过门禁。
- 本项没有真实购买方腾讯、阿里云、腾讯云短信或短信宝账号，未发送计费请求。供应商边界以官方契约、适配器单元测试、本地网关假服务和安全门禁验证，不能冒充购买方正式账号验收。

## 影响判断

- 数据权限：客户接口始终从可信登录上下文取得当前客户和企业归属，不接受调用方传入其他客户号；后台候选与提交使用精确合同创建权限。列表固定有界查询，不逐行回查，不产生随行数增长的`N+1`查询。
- 数据库：迁移`012`保存独立签署经办人和验证历史，迁移`013`只保存本地合规网关路由；均使用本地 PostgreSQL 约束和索引。签署预留和最终状态继续使用 PostgreSQL 权威行锁与事务级 advisory lock，目的是同时锁定合同号和幂等摘要，避免两个进程各自越过腾讯写边界。
- 审计：开始提交和最终状态都与对应业务写入同一事务。审计失败时业务状态失败关闭，不会留下无审计状态。
- `i18n`：合规插件合同成品文案按模板明确选择的中文或英文装配，不读取管理员当前界面语言；客户页面双语键和真实中文页面已通过验证。
- 缓存：本项不新增缓存；签署候选、预览和提交均读取数据库权威状态或不可修改快照，因此无缓存一致性影响。
- 开发工具与安装：本项未修改公共构建或测试工具。网关仍是每套安装随附并由本地监管的独立进程；没有中央业务网关、中央结算、平台销售注册或软件提供方业务回调依赖。
- 插件规则：`idc-notify`与`idc-compliance`根目录均没有插件本地`AGENTS.md`，因此使用项目顶层规则。旧 Portal 没有删除或写入。
