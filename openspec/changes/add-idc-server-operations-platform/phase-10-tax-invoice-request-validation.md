# 第 10 阶段发票申请验证记录

## 记录范围

- 日期：2026-08-17
- 对应任务：`10.11.b`
- 本记录只证明供应商中立的发票申请、快照、金额分配、占用计算、并发防超额和精确幂等已经在合规插件完成。
- 本记录不证明后台审核、供应商提交、退款红冲、客户页面或诺诺真实接入已经完成；这些分别属于`10.11.c`、`10.11.d`、`10.12`和外部证据门禁后的`10.11.e`。

## 已冻结的业务规则

- 客户提交后固定进入`pending_review`，并立即占用本次申请金额。
- `failed`和`result_unknown`继续占用额度；只有开具前被后台明确驳回为`rejected`，或明确取消为`canceled`，才释放占用。
- 已开具、已交付和红字相关状态不按“取消申请”直接释放，后续由退款与红字分配任务处理。
- 客户不能选择票种；新申请以`pending_confirmation`记录，后续由有权后台人员选择本地供应商真实支持的票种。
- 浏览器只提供抬头编号、账单编号、每张账单的本次金额和幂等键；销售方、税目、税率、未税金额与税额都取自服务端冻结的来源事实。

## 实现与边界

### 不可变申请与快照

- 合规插件新增`taxinvoicerequest`服务，负责创建当前登录客户自己的发票申请和读取已占用额度。
- 申请头、销售方快照摘要、购买方快照摘要、逐账单分配和逐项明细在同一数据库事务写入。
- 完整敏感快照使用合规插件自己的`compliance.tax-invoice-snapshot`秘密范围密封；业务表只保存不透明引用和 SHA-256 摘要，不保存银行等敏感明文。
- 数据库触发器禁止删除法定申请记录，禁止修改客户提交事实、来源分配和逐项明细；后续状态、票种和供应商处理字段仍可按受控状态机更新。
- 发票明细新增不可为空的分配编号和核心账单明细不透明编号，并用复合外键保证明细一定属于本申请的正确账单分配。

### 部分、合并与剩余额度

- 一次申请最多选择`20`张已付款账单，合计最多`200`条税务明细。
- 每张账单可以只申请部分金额，也可以把多张同币种账单合并成一份申请。
- 核心来源能力锁住所选账单，按既有占用计算剩余额度；合规插件在锁释放前完成申请、分配和明细写入。
- 占用读取固定执行两次分组查询：一次汇总逐账单分配，一次汇总逐项金额；没有在账单或明细循环中查询数据库。
- 占用查询同时绑定安装实例固定租户、当前客户编号和有上限的账单编号集合，不能借编号查看其他客户的申请存在性或金额。

### 并发与精确幂等

- 幂等键先绑定当前客户，再与规范化后的抬头和金额选择共同生成请求摘要；数组顺序变化不会产生新申请。
- 同一客户、同一幂等键、相同内容会返回原申请；相同幂等键但内容变化会明确冲突，不会静默复用。
- 稳定申请编号使用事务级数据库锁串行保护；不同幂等键同时申请同一账单时，核心账单行锁保证重新读取最新占用。
- 真实 PostgreSQL 并发用例中，两笔各申请`700`、来源额度总计`1000`的请求同时提交，结果固定为一笔成功、一笔被拒绝，最终占用为`700`，没有超开。

### 依赖装配

- 服务由合规插件`internal/composition`构造，依赖安装实例共享数据库、核心插件公开的`taxinvoicecap.Service`以及合规插件自己的秘密访问器。
- 合规插件没有读取核心插件内部包、DAO 或数据表；核心插件也只通过公开的`AllocationUsageReader`回调读取合规插件计算出的有限占用投影。
- 本任务没有把服务注册到 HTTP 路由，也没有构造任何诺诺或其他真实供应商客户端；HTTP 与页面接线留给`10.12`，审核与供应商提交留给`10.11.c`。

## 数据库与代码生成

- 新增`manifest/sql/019-tax-invoice-request.sql`，内容为当前迭代 DDL，不含生产业务数据 DML。
- 迁移可重复执行；约束、索引、函数和触发器均使用可重复创建或替换方式。
- 项目是全新项目，不承担旧数据兼容；如果已经存在没有来源归属的发票明细，迁移会明确失败，避免把未知旧数据错误归属。
- 使用专用临时 PostgreSQL 数据库执行插件安装迁移后，按仓库既有`linactl dao`入口重新生成 DAO、DO 和 Entity；没有手工维护生成字段。
- 发票申请和分配不使用软删除，因为这些是需要保留的法定追溯记录。
