# 第十阶段业务请求认证准入验证记录

## 1. 任务结论

任务`10.6.d.2`已经完成中央网关内部的活动实例验签、数据库权威时间窗、防重放、业务幂等恢复和实例/操作两级持久限流。所有准入状态在调用任何业务处理器或供应商之前提交；当前仍没有注册之外的业务 HTTP 路由，也没有供应商调用。

## 2. 验签与事务重检

- 服务端先根据路由注入的预期操作范围、实际方法、规范路径/查询和收到的原始载荷重新计算投影，与签名证明逐字段核对；载荷超过 1 MiB、范围漂移、目标漂移或摘要不一致均在数据库写入前拒绝。
- 服务读取精确活动实例与活动密钥公钥，验证`lrp1`完整`Ed25519`签名；进入 PostgreSQL 事务后再次锁定实例和密钥，并核对活动状态及公钥指纹，避免验签后的轮换或撤销竞态。
- 事务使用 PostgreSQL 权威时间要求尚未到期，且客户端签发时间最多超前三十秒。应用进程时间不构成准入事实；过期、未来漂移、已撤销实例或已退役密钥均返回统一身份拒绝。
- 业务幂等键使用独立`RequestDigester`和固定用途域计算 HMAC。该密钥与注册令牌、身份操作和供应商主体查重密钥分别构造、分别清除。

## 3. 防重放、幂等与限流

- PostgreSQL 先按业务幂等 HMAC 取得事务级 advisory lock，再锁定活动实例/密钥并查询随机数和业务请求。同一幂等键改变业务内容返回`request_conflict`；同一随机数改变签名帧、密钥或业务请求同样冲突。
- 完全相同的已登记签名帧直接恢复原请求和当前状态，不增加限流计数。相同业务幂等键使用新时间、随机数或轮换后的新活动密钥时，登记新的传输随机数、经过两级限流后恢复同一业务请求，不创建第二条业务事实。
- 新业务请求、随机数、实例限流计数和操作限流计数位于同一事务。任何一层超限、唯一冲突或数据库错误都会整体回滚，不消耗另一层计数，也不留下半条请求或随机数。
- 每个限流维度使用数据库固定窗口和行锁。相同策略版本不得静默改变窗口或上限；更高版本显式重置新窗口，过期窗口以数据库时间重置，低于数据库版本的陈旧配置失败关闭。`rate_limited`错误只暴露稳定码和最长一小时的受控重试间隔。

## 5. 规则域与审查

- 架构、插件与 API：实现闭环在中央网关内部服务和 PostgreSQL 存储，没有修改宿主、商家插件 API、后台或 Portal，也没有开放业务路由。
- 数据权限：认证器必须由未来路由传入服务端预期操作范围；当前没有可绕过的公共入口。目标业务对象仍需在后续业务服务内独立授权，认证成功不等于合同或发票权限。
- 数据库与性能：单次准入只处理一个实例、一个密钥、一个随机数、一个业务请求和固定两个限流维度；全部使用唯一索引、精确查询和行锁，无列表、扫描或`N+1`。
- 安全：私钥、幂等键、随机数和载荷原文不落库；错误响应只提供稳定代码。已撤销实例不允许凭旧幂等键恢复历史业务存在性。
- 缓存、前端、宿主与`i18n`：无影响。

`lina-review`复核了路由范围绑定、实际载荷摘要、验签后状态竞态、随机数/幂等锁顺序、限流回滚、策略降级、密钥轮换恢复和撤销后存在性保护。审查期间补充了公开操作范围规范器、限流状态更新精确行数校验、并发限流回归和策略版本变更回归；最终没有遗留阻断`10.6.d.2`的`P0`、`P1`或`P2`问题。
