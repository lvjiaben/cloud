## 结论

`FB-52`不是普通缺陷，而是平台底座纠偏。当前代码把首批服务器业务误当成通用商品边界，又把首批交付方式误当成所有插件必须采用的运行和分发方式。任何依赖这两个假设的后续实现立即暂停；不得加兼容层掩盖，也不得用服务器单一场景证明通用模型完成。

## 根因

问题由四组旧假设共同造成：

1. 旧商品任务把分类、商品类型、配置组和发布版本直接绑定云服务器、裸金属、地区、线路、处理器、内存、磁盘、带宽和镜像。
2. 旧交易与服务实现继续把上述服务器字段带入购物车、报价、订单项、履约单元和服务实例，使非服务器商品无法只靠插件接入。
3. 旧插件骨架把正式业务插件普遍建立为`source + builtin`，智简魔方连接器也被编译进源码；清单没有把运行类型、分发方式、业务扩展点和前端表面分开。
4. 旧命名把`linapro-`写入官方插件目录、路由、权限、菜单、语言命名空间和数据库表前缀，并形成大量测试和验证记录。项目没有上线兼容负担，这些名称不能继续成为新契约。

智简魔方财务源码只作为`clean-room`业务参考。`Product.php`、`ConfigOptions.php`、`Provision.php`、`PluginLogic.php`与`Menu.php`证明了商品、配置、自动开通模块和插件菜单是可分离的扩展概念；它同时存在固定商品类型、逐项查询和服务器动作耦合，因此不能复制其实现或数据库结构。LinaPro采用通用商品版本、受治理扩展点、持久异步任务和批量装配重新实现。

## 强制模型

- 商家自定义分类和任意商品；分类名称不决定商品类型。
- 核心商品、购物车、报价、订单、账单、服务和履约模型不包含任何特定商品字段。
- 每个已发布商品版本最多冻结一个自动化接口实例；供应商切换必须发布新版本。
- 商品只允许完全人工、审核后异步插件、付款后异步插件三种履约。
- 插件清单分别声明运行类型、分发方式、业务扩展点、后台表面和客户中心表面。
- 商品履约、短信渠道、支付方式和官网模板至少作为四个版本化扩展点，由各自内置业务拥有方授权和治理。
- 动态插件页面安全隔离，不取得原始令牌或宿主全局状态，同时必须保持主题、语言、布局和加载体验连续。
- 停止新业务只阻止新绑定、新购买和新任务；已有服务能力保留，排空或迁移后才能停用或卸载。
- 插件管理只展示托管插件；`tenant-core`及稳定拥有方是隐藏、强制启用、不可卸载的内置插件。
- 所有官方插件标识一次性移除`linapro-`，不保留旧名称、重定向或兼容层。
- 服务器能力迁入服务器插件契约；智简魔方公有云作为托管动态服务器连接器，不再代表通用商品自动化。

## 实施顺序
