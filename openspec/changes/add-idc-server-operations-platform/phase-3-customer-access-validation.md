# 第三阶段客户访问门禁验证记录

## 范围与完成判断

- 本记录覆盖任务 3.3.a：客户域统一访问守卫、直接活动客户路由门禁、可信请求主体投影，以及数据库查询前的客户编号归属校验。
- `AccessGuard`由宿主业务上下文和`principal.Service`显式构造，不读取角色名称、请求参数或宿主数据库推断客户身份。
- 现有资料、法定资料变更、注销申请和数据导出服务已复用同一守卫，避免路由与领域服务分别维护两套身份判定。
- `customer.New`把启动期共享`AccessGuard`作为必需构造参数，不在业务构造函数或请求路径创建第二套守卫。未来运行时装配由`idc-core`路由注册回调使用宿主`BizCtx`和启动期`principal.Service`创建一次，再把同一实例传给客户中间件和自助服务。
- 当前插件尚未交付客户`HTTP API`和 Controller，因此守卫尚无真实路由可装配。任务 3.3 保持未勾选，仅勾选 3.3.a；后续不得用“中间件类型已存在”替代逐接口的数据归属验证。

## 身份与所有权边界

客户请求必须同时满足以下条件：

1. 宿主上下文存在有效用户，且不是模拟、代操作、租户代入、超级管理员或平台绕过上下文。
2. 当前上下文不带任何`idc:admin:*`管理权限。
3. `principal.Service`返回同一用户的唯一、活动`customer`受众和合法客户编号。
4. 带目标客户编号的接口必须在语法校验和数据库访问之前比较目标编号与可信绑定。

缺少绑定、绑定异常、受众非客户、受众已撤销、编号格式错误、外部编号和不存在编号统一返回`IDC_CUSTOMER_NOT_ACCESSIBLE`。守卫不根据失败原因暴露对象是否存在，也不把超级管理员自动降级成客户。

中间件只把`user_id + customer_no`不可变最小投影写入私有类型键的请求上下文，不写入资料、法定身份、权限或凭据。后续 Controller 和领域服务复用该投影时不再次查询受众；目标编号仍必须调用`RequireOwned`，不能把“通过客户路由”解释为拥有任意客户对象。

## 装配与数据权限要求

- 未来客户路由固定先执行宿主`Auth`和`Tenancy`，再执行活动客户绑定与所有权守卫；客户自助权限不得复用后台菜单权限。
- 当前客户资料服务即使在没有 HTTP 中间件的内部调用中，也会通过同一个守卫重新解析可信主体，保持纵深防御。
- 联系人、地址、账单、订单、服务、工单、附件下载和聚合接口落地时，必须在各自数据库查询条件中固定可信`customer_no`。`AccessGuard`不能替代查询层的行级过滤。
- 管理后台继续使用独立员工受众、精确权限和目标数据范围授权器，不得经过客户自助守卫取得写能力。
