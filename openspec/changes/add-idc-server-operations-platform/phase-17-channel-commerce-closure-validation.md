# 第十七阶段渠道商务闭环验证记录

本轮按用户确认的推荐模型完成`17.4`、`17.5`和`17.8`。渠道企业承担付款、信用和结算责任；服务所有者可以是渠道自身，也可以是渠道委托的终端客户。首次出现的委托客户只建立不可登录、待激活、待实名的客户记录，在客户自行激活并完成实名前，系统不允许结算或触发上游履约。

## 生产闭环

| 范围 | 已完成结果 |
|---|---|
| 订单与主体 | 核心订单、报价和服务事实分别保存付款方与服务所有者；重复请求复用同一事实，改变载荷拒绝，不用渠道编号绕过客户与数据权限。 |
| 生命周期 | 续费、重装、控制台、终止走统一业务操作；变配与换`IP`先预览并冻结报价、版本与资源预留，确认后才结算和派发任务。升配即时，降配到期生效；零金额操作不伪造账单。 |
| 执行与恢复 | 异步执行器按批次领取和派发任务，记录请求摘要、上游任务证据、成功、失败、结果未知、退款或人工接管事件；重启后从持久化事实继续，不靠进程内状态猜结果。 |
| 财务与停用 | 管理与渠道 API 从统一核心事实投影逐币种余额、信用、应收、实收、退款和成本；渠道停用后禁止新购及收费生命周期动作，仍可查看历史服务、财务、还款和售后信息。 |
| 管理页面 | 渠道、商品发布、令牌、额度、健康、请求审计和结算均有真实 API 与状态页面，不再用“尚未开放”占位。 |
| 客户页面 | Vben 客户后台提供渠道令牌自助创建、一次显示、列表和撤销；只对商家已批准且已实名的企业渠道开放。页面隐藏数据库编号和原始作用域代码，使用业务名称、日期选择器和友好失败提示。 |

## 数据、接口与架构审查

- `idc-core`通过公开`channelcommercecap`和`serveroperationresourcecap`承接交易、财务、实名、服务与资源执行事实，`idc-channel`只依赖公开能力，不导入其他插件的`internal`实现。运行时在启动装配时取得共享数据库、资源来源、IP 容量来源和审计来源，执行器没有另建不一致的私有状态。
- `104-channel-service-operation.sql`、`105-channel-priced-service-operation.sql`和渠道插件`004-channel-commerce-management.sql`均可重复执行；真实 PostgreSQL 已顺序执行并重放关键迁移，所有新增插入语句还经过`PREPARE`验证。
- 公共 API 时间统一为 Unix 毫秒，输入到期时间也使用毫秒；前端使用日期选择器，不要求用户填写`RFC3339`。请求采用严格 JSON，未知字段和无效金额、版本、作用域、来源网段均失败关闭。
- 客户接口从当前登录客户解析资格，渠道接口从令牌解析唯一渠道和作用域，管理接口要求精确权限并显式选择渠道；跨渠道编号统一不可见，撤销令牌立即失效。
- 列表和管理投影采用有界集合查询；异步执行器按批次处理，没有随返回行数逐项查询的`N+1`路径。此次没有新增缓存，也没有修改构建、代码生成或开发工具，因此缓存一致性和开发工具规则判定为无影响。
- 用户可见文案均进入插件双语资源或页面本地化边界，运行时中文扫描、消息覆盖和前端 key 覆盖均为零违规。

## 任务级`lina-review`

活动变更的插件和 OpenSpec 目录原本整体处于未跟踪共享基线，Git 不能可靠区分本轮与既有文件数量；本轮按功能面逐文件审查了两个插件的渠道商务运行时、三份新增迁移、账户/管理/渠道三组 API 与控制器、管理和客户两端页面、四个渠道 E2E 文件及页面对象。审查覆盖架构/DI、数据权限、接口契约、数据库、性能、前端、测试、文档和`i18n`规则。

审查发现并在本轮修正了三类问题：客户页面曾显示数据库令牌编号、原始作用域代码和技术日期格式，并在拒绝时透出后端原始错误；公共 API 的时间字段曾混用字符串与 Go 时间对象；七个渠道商务函数超过仓库复杂度门禁。修正后页面只显示业务名称和友好提示，接口统一 Unix 毫秒，复杂函数拆成保持同一事务和错误语义的校验/持久化助手。最终没有遗留本地阻断项。
