# 已付款云服务器失败恢复验收

## 范围与根因

本记录对应`PROVISION16`至`PROVISION20`。只修改`idc-core`、`idc-resource`插件及其测试和规范，沿用原成交规格、原金额、管理员处理权限和未知结果禁止重发的边界。

实际发现并修正了以下断点：

- 服务器绑定通知在权益刚进入待激活时就开始消费，尚未开通便耗费本地投递次数；核心成功但资源结果仍在本地回报时还会再退避三十秒。
- 更换上游需要新建客户账户时，账户准备任务与等待中的服务器重开事务一起回滚，独立账户任务无法执行。
- 重开成功后的服务器绑定把原成交接口当作本次执行接口，换渠道后无法进入客户服务器列表。
- 新渠道首次能力发现失败被当作五分钟内的新鲜记录，短暂装配失败会挡住后续开通；旧失败渠道也可能占据批次。
- 本地进度查询改为五秒后，持续正常运行的资源任务可能在第四十五秒就耗尽核心十次查询预算，提前进入人工处理。

## 实现约束

本地绑定等待相同客户、意图的权益激活及当前资源任务结果回报，不消耗失败次数；历史失败结果不挡住新成功任务。合法管理员恢复可重新安排耗尽的纯本地绑定投影，原状态、次数和原因保留在同一业务审计。活跃租约、已交付权益、其他客户及其他拥有方不能重置。

账户准备先验证明确未受理、原凭据已撤销、没有任务绑定或活动资源，再独立提交账户准备任务；创建服务器后继前仍持锁重复核对。重复命令只返回同一后继。

资源任务额外保留原成交接口事实，配置修正只决定实际执行接口。绑定同时核对原成交身份和当前执行身份；客户后续读取采用真实执行渠道，原订单及资金身份不变。旧普通任务缺少新增私有字段时仅按原接口匹配，不将新渠道伪装为原成交。

完整能力矩阵仍为五分钟刷新，失败发现三十秒后可重试，未发现的渠道优先。每批固定最多八项，只对已提交失败记录继续其他项，存储错误中止。完整矩阵和条目原子提交，保留旧完整记录、渠道启用及版本围栏。权威数据是当前启用连接器声明，快照保存在共享数据库；主节点任务负责刷新，资源执行已有的证据有效期不变，未引入进程本地缓存。

首次运行进度仍及时确认，重复确认仍正常运行的资源任务恢复原三十秒等待。原次数上限、受理事实、失败与未知结果围栏、租约及版本保护均保留。

新增`039-provisioning-coordination-indexes.sql`只包含两个幂等索引：成功资源回执的原成交身份查找，以及渠道最近完整或失败能力发现的时间排序。没有新增字段、种子或模拟数据，无需生成新的`DAO/DO/Entity`。

## 隔离验证

## 任务级审查

按`lina-review`检查上述生产文件、新增未跟踪测试、迁移及本记录。新增运行期依赖为零：沿用启动装配传入的数据库、连接器会话工厂、资源源接口、账户准备回调及拥有方路由。账户准备由资源插件声明装配的原`principal.EnsureForPool`持久化，不在恢复方法里创建服务图或直接发起供应商开通。

数据权限沿用管理员恢复入口的目标可见性、付款和版本核验；后台任务只处理内部租户及精确拥有方事件，资源绑定重新验证客户与原成交身份。没有新增绕过身份的公开入口。所有集合查询在数据库侧过滤，能力批次固定八项、本地绑定固定一项，配套索引覆盖新增历史查找，不按页面行数逐条查上游。

触发`E2E`质量审查，依据为完整付款和重开工作流。断言覆盖真实订单金额、原规格、脱敏响应、未知保护、双命令幂等、真实连接器请求及客户服务器归属，不能仅靠按钮或接口返回成功验收。此次为接口和后台任务联动，没有修改页面结构，因此这些用例不伪造浏览器截图；已有页面验证保留在对应记录。

当前范围审查未发现阻塞问题。本地已启用`idc-core v0.1.153`及`idc-resource v0.1.54`，冻结连接器仍为`idc-zjmfcloud v0.3.9`；三者运行状态正常，证据为`090800-recovery-installed-proof.json`。正式构建没有测试传输覆盖，安装前队列检查为空，两个索引安装后核对存在，分别见`085700-recovery-final-queue-read.json`及`091000-installed-index-proof.json`。后台静态资源继续使用已验证的商品抽屉构建，没有恢复旧资源。

`091000-real-order-readonly-proof.log`通过统一只读入口核对原`ORD_669509692287eaaf490d8c3a871399b5`：已付款事实保留，仍为原未知资源任务、三次执行且没有上游绑定，没有自动重开、退款或补造接口正文。历史缺失正文不能追溯恢复，仍须管理员按已有入口人工核对后处理。未代理管理员确认、开通、退款或其他第三方写入。
