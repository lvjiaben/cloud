# 开通失败由管理员选择处理

## 本次范围与结论

按`lina-feedback`归入当前活跃变更。用户已确认：未来确定失败的开通由管理员选择重新开通或退款，不自动退款、不重复收费。本次不处理当前陕西订单，不执行第三方写入。

根因包括：停止调度的任务仍投影为处理中；原恢复入口只覆盖提交前准备失败；后台只有退款审核而没有失败履约的退款发起入口；原结果回报及资源回执唯一约束无法保留同一原单的多次失败和后续成功。

源码、隔离验证及本地运行切换已完成。切换前只读确认履约、资源提交及上游用户创建和清理队列为空，随后启用新后台；核心和资源迁移由正常启动升级流程自动执行，动态连接器和客户模板通过现有插件升级入口更新。此结论不代表当前订单已交付、已退款或第三方真实开通已重新验收。

## 实现与边界

- 自动任务停止、结果未知或查询预算耗尽后投影为`manual_processing`，后台可单独筛选；客户保留已付款标识并停止轮询。明确拒绝仍为处理未完成。
- 管理员重新开通使用原付款和冻结配置，独立校验恢复权限、数据范围、原因、说明、版本及退款围栏。旧任务不重置，累计计数保留；资源拥有方只给确定拒绝、无绑定或有效映射、已回报失败且撤销旧凭据的任务追加唯一后继。
- 新退款入口复用`idc:admin:billing:refund:review`及财务拥有方。以原账单付款人、原资金分配和现有审批策略发起退款，保留审计；退款申请不等于退款成功。未知、已受理、无明确拒绝证据、版本过期或审计失败均拒绝。
- 退款与恢复按原履约及账单加锁，已有相关退款时拒绝恢复；对已有非拒绝退款的订单项保守阻止再次发起，不绕过财务数量和金额规则。
- 运行依赖在启动装配注入同一数据库、财务授权、审计及授信退款实例。退款服务内部复用同包退款命令实现，不构造客户身份、不使用请求级全局服务查找；无新增缓存。
- 新迁移为核心`139-rejected-fulfillment-recovery.sql`和资源`037-rejected-provision-recovery.sql`。前者使一个核心任务可分别回报多个资源尝试，后者保留失败回执历史且仍保证同一冻结拥有关系只有一个成功回执；没有新增或手写`DAO/DO/Entity`。
